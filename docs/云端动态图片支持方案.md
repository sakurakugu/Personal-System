# 云端动态图片支持方案

## 背景

当前云端动态模块只有 `title` 和 `content` 两个核心内容字段，前端编辑区也只有标题和文本输入框。虽然详情页会把正文按 Markdown 渲染，但并没有正式的图片上传入口、图片列表、排序、删除和数量限制能力。

这会带来几个问题：

- 用户无法直接上传动态图片，只能手动插入外部链接或站内链接。
- 动态图片没有结构化数据，首页流和详情页无法稳定展示图片列表。
- 草稿发布时会删除草稿再创建新动态，若未来图片绑定到动态实体，这个流程会导致图片关联丢失。

因此需要为动态增加正式的图片上传与展示能力。

## 目标

- 在动态输入框下方新增图片上传入口。
- 点击上传入口后显示图片区域，图片区域位于输入框下面。
- 图片区域支持点击上传和拖拽上传。
- 图片区域默认一行横向展示缩略图。
- 单条动态最多允许 20 张图片。
- 支持删除图片。
- 支持调整图片顺序。
- 动态详情页可展示图片列表。
- 首页动态卡片和后台动态列表可按需要展示首图或图片数量。

## 核心设计结论

### 业务上单独建立动态图片区

不建议和文章图片区共用业务模型或存储区域，推荐单独建立动态图片能力。

原因如下：

- 文章图片当前强绑定 `article_id`，语义明确，权限判断依赖文章可见性。
- 动态图片属于另一类内容资源，后续更可能需要首图、排序、横向滑动、多图布局等独立能力。
- 如果把动态图片塞进文章图片模型，会让权限、清理、展示逻辑越来越混乱。

因此推荐：

- 元数据：新增 `moment_images` 表。
- 对象存储目录：新增 `moments/{moment_id}` 目录。

### 技术上复用现有上传基础设施

虽然业务上分开，但底层能力应尽量复用现有文件上传基础设施：

- 图片类型校验
- 10MB 大小限制
- 静态图片压缩
- 站内文件签名 URL
- 缩略图生成
- 对象存储上传与删除

这样可以减少重复代码，保持图片处理规则一致。

## 数据模型设计

### 动态主表

现有 `moments` 表保留，但需要调整发布流程语义：

- 草稿仍然使用 `moments` 表中的 `is_published = false`
- 发布时不再删除草稿后新建记录
- 改为把草稿原地转为已发布状态

这样做的原因是图片记录将通过 `moment_id` 绑定到动态，如果发布时换一条新记录，图片关联会全部断掉。

### 动态图片表

新增 `moment_images` 表，建议字段如下：

- `id`
- `moment_id`
- `original_name`
- `storage_key`
- `size`
- `mime_type`
- `sort_order`
- `created_at`

约束与索引建议：

- `moment_id + sort_order` 建索引，便于按顺序读取
- `storage_key` 唯一
- `moment_id` 外键级联删除

## 接口设计

### 草稿与发布

保留现有接口路径，但调整返回结构，返回动态时附带图片列表。

- `GET /moments/draft`
- `PUT /moments/draft`
- `POST /moments/publish`

发布逻辑改为：

1. 获取当前用户草稿
2. 若不存在草稿则创建一条动态并直接发布
3. 若存在草稿则原地更新其 `title`、`content`
4. 将 `is_published` 改为 `true`
5. 设置 `published_at`
6. 保留当前草稿关联的全部图片

### 动态图片管理

建议新增接口：

- `GET /moments/{moment_id}/images`
  用于获取当前动态的全部图片，按 `sort_order` 升序返回。

- `POST /moments/{moment_id}/images`
  上传单张图片并返回图片信息。

- `PATCH /moments/{moment_id}/images/order`
  批量更新图片顺序。

- `DELETE /moments/{moment_id}/images/{image_id}`
  删除单张动态图片。

### 草稿图片上传前置处理

动态编辑页可能在“还没有草稿记录”时就开始上传图片，因此需要一个前置保证：

- 上传图片前，若当前没有草稿 ID，则先自动创建或保存草稿
- 再使用该草稿对应的 `moment_id` 进行图片上传

这和文章编辑器“上传图片前先确保草稿存在”的策略一致。

## 前端交互设计

### 编辑区布局

在后台首页的动态编辑卡片中调整为：

1. 标题输入框
2. 内容输入框
3. 图片入口栏
4. 图片横向列表
5. 底部操作按钮

### 图片入口

图片入口区包含：

- “图片”按钮
- 当前图片数量提示，如 `3 / 20`
- 拖拽提示

行为：

- 点击“图片”按钮后展开图片区域
- 若已展开，再次点击可收起
- 当已有图片时，即使收起，也保留数量提示

### 图片区域

图片区域放在输入框下方，采用一行横向滚动布局。

每张图片卡片包含：

- 缩略图
- 上传中状态
- 删除按钮
- 拖拽排序手柄或直接拖拽排序

交互要求：

- 支持拖拽文件到整个图片区上传
- 支持多文件一次上传
- 超过 20 张时阻止继续上传
- 非图片文件给出提示
- 单张上传失败时保留其他成功项

### 数据编辑策略

动态正文 `content` 与图片列表分离存储：

- `content` 继续保存纯文本或 Markdown
- 图片单独作为 `images` 数组返回

不建议再把上传图片自动拼接进 Markdown 正文，避免正文和图片区双重表达。

## 展示策略

### 动态详情页

详情页展示顺序建议为：

1. 作者信息
2. 标题
3. 正文文字
4. 图片列表
5. 点赞区

图片展示建议使用响应式网格或单列卡片，首版可先做简单宫格。

### 首页动态卡片

首页流中的动态卡片不再只截文本摘要，建议补充以下能力之一：

- 有图时显示首张缩略图
- 或显示图片数量标签，如“3 图”

首版为了降低改动范围，可以先只显示图片数量标签，详情页完整展示。

## 权限与访问控制

动态图片应跟随动态权限，而不是文章权限。

访问规则建议：

- 已发布动态图片：按动态详情的访问权限控制
- 草稿动态图片：仅作者可访问

由于当前 `/files/{storage_key}` 路由已经对文章图片和普通文件做了权限区分，后续需要把动态图片也接入这层权限判断。

## 实现顺序

建议按以下顺序开发：

1. 新增 `moment_images` 模型与 Alembic 迁移
2. 调整动态发布逻辑为草稿原地发布
3. 新增动态图片的查询、上传、删除、排序接口
4. 调整动态详情与列表响应，附带图片数组
5. 前端增加动态图片类型定义和 API
6. 前端实现上传入口、拖拽区、横向图片列表
7. 前端补充详情页图片展示
8. 完成检查与回归测试

## 首版范围

首版建议先实现以下最小闭环：

- 动态可上传最多 20 张图片
- 后台编辑页可点击和拖拽上传
- 可删除图片
- 可调整顺序
- 发布后图片保留
- 详情页能显示图片

以下内容可以放到后续增强：

- 首页流首图预览
- 图片批量删除
- 图片查看大图弹层
- 图片上传进度条优化
- 图片粘贴上传

## 风险点

- 需要调整动态发布语义，避免草稿删除后图片关联丢失。
- 需要同步修改文件访问权限逻辑，否则动态图片可能无法正常访问。
- 需要注意首页、详情页、后台列表三处返回结构变化带来的类型联动。
- 前端拖拽排序如果选型过重，可能影响首版交付速度，首版可先采用轻量实现。
