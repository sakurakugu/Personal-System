# 前端统一架构方案

## 目标

这次统一前端的目标，不是把云端、桌面端、手机端强行做成一套完全相同的页面，而是把重复建设最多的部分收敛到统一层，同时保留各端自己的产品边界。

核心目标如下：

- 统一业务模块，避免同一套业务在三端重复写
- 统一接口访问、状态模型、主题机制、路由守卫等基础能力
- 保留平台差异，允许各端继续拥有独有页面、独有能力、独有布局
- 避免公共层被 `if (platform === ...)` 污染
- 支持后续继续扩展桌面端本地 AI、手机端课程表、云端首页轮播图等能力

## 先说结论

推荐采用下面这套结构：

- `apps/*` 负责平台壳层
- `packages/api` 负责统一接口访问层
- `packages/domain` 负责纯业务领域状态与流程
- `packages/modules` 负责跨端复用的前端业务模块分组目录，目录下每个模块都是独立 workspace 包
- `packages/platform` 负责平台能力抽象与各端适配
- `packages/ui` 与 `packages/theme` 负责视觉基础层
- 可跨端复用的启动流程建议新增 `packages/app` 或 `packages/app-core`

这套方案的重点不是“页面完全统一”，而是“模块统一，装配分端”。

## 为什么不建议直接共用整套页面

从当前仓库现状看：

- `apps/phone` 和 `apps/desktop` 的启动流程已经比较接近
- `packages/api`、`packages/domain`、`packages/theme`、`packages/ui` 已经是共享雏形
- `apps/cloud/frontend` 的业务更多，包含博客首页、后台管理、工具台、文件管理等重页面能力

这说明现在最值得统一的是：

- 认证逻辑
- 接口运行时
- 主题状态
- 通用业务模块
- 路由守卫
- 平台能力抽象

不值得强行统一的是：

- 云端博客首页的展示形态
- 手机端底部导航和移动端交互
- 桌面端工具台、本地 AI、本地文件能力
- 各端根布局

如果把这些页面也硬揉成一套，最终公共层里会充满平台分支，后面维护成本会更高。

## 推荐的总体分层

```text
apps/
  cloud/frontend/         # 云端壳层：博客、控制台、云端专属模块装配
  desktop/                # 桌面壳层：Tauri、本地能力、桌面专属模块装配
  phone/                  # 手机壳层：Capacitor、移动导航、手机专属模块装配

packages/
  api/                    # 统一接口客户端、运行时、错误处理、上下文
  domain/                 # 纯业务领域模型、store、业务流程
  modules/                # 前端业务模块，按业务拆分
  platform/               # 平台能力抽象、适配器、平台实现
  app-core/               # 前端应用公共装配层，可新建
  ui/                     # 通用基础组件
  theme/                  # 主题 token、主题状态、色相能力
```

其中每层职责要明确。

### `apps/*` 的职责

每个应用目录只负责下面这些事情：

- 应用入口
- 根布局
- 路由装配
- 平台能力注册
- 平台专属模块注册
- 原生桥接
- 应用级样式覆盖

简单说，`apps/*` 不负责沉淀通用业务，它负责“把公共能力装起来”。

### `packages/domain` 的职责

这里放纯业务领域能力：

- 类型定义
- 领域 store
- 业务规则
- 领域 API 封装
- 与界面无关的业务流程

这里不要直接依赖：

- `window`
- `document`
- Tauri API
- Capacitor API
- 具体 Vue 页面组件

### `packages/modules` 的职责

这里是这次统一前端的核心层。

建议按业务模块拆，而不是按平台拆，例如：

```text
packages/modules/
  auth/          # -> @personal-system/module-auth
  profile/       # -> @personal-system/module-profile
  todos/         # -> @personal-system/module-todos
  calendar/
  blog/          # -> @personal-system/module-blog
  files/
  local-ai/
  banner/
```

每个模块内部再按前端职责拆分，例如：

```text
packages/modules/todos/
  package.json
  src/
    pages/
    components/
    composables/
    routes.ts
    nav.ts
    install.ts
    index.ts
```

应用侧统一通过包名导入，而不是通过 `tsconfig paths` 直连源码目录。例如：

```ts
import { createAuthModule } from '@personal-system/module-auth'
import { TodosPage } from '@personal-system/module-todos'
```

这里的原则是：

- 相同业务优先进入同一个 `modules/<name>`
- 模块可以提供页面、组件、路由、导航项、安装函数
- 模块内部可以声明自己依赖哪些平台能力
- 一个模块可以被多个端注册，但不要求所有端都注册

### `packages/platform` 的职责

这里不要只放零散工具，建议正式升级成“平台能力层”。

例如可以统一抽象这些能力：

- 存储能力
- 认证会话能力
- 本地文件能力
- 本地 AI 能力
- 系统主题同步能力
- 课程表本地读取能力
- 轮播图配置管理能力

建议结构类似：

```text
packages/platform/
  src/
    core/
      capabilities.ts
      context.ts
    adapters/
      browser/
      capacitor/
      tauri/
```

这样公共模块只依赖能力接口，不依赖具体平台实现。

### `packages/app-core` 的职责

这个包当前仓库里还没有正式建立，但我建议补上。

它负责收敛现在三端重复的前端应用装配逻辑，例如：

- 主题初始化
- hue 初始化
- 登录恢复
- 路由守卫
- 公共 app bootstrap
- 模块注册机制
- 导航汇总机制

从当前代码看，下面几处已经有明显重复：

- `apps/phone/src/app/bootstrap.ts`
- `apps/desktop/src/app/bootstrap.ts`
- `apps/cloud/frontend/src/app/bootstrap.ts`

这部分非常适合进入 `packages/app-core`。

## 模块统一，平台分端

最推荐的运行方式，是每个端都维护自己的“模块清单”，而不是试图共享一份总路由。

例如：

```ts
// apps/phone/src/app/modules.ts
export const phoneModules = [
  authModule,
  todosModule,
  profileModule,
  calendarModule,
]
```

```ts
// apps/desktop/src/app/modules.ts
export const desktopModules = [
  authModule,
  todosModule,
  profileModule,
  localAiModule,
]
```

```ts
// apps/cloud/frontend/src/app/modules.ts
export const cloudModules = [
  authModule,
  blogModule,
  filesModule,
  todosModule,
  bannerModule,
]
```

这样做的好处很直接：

- 业务模块只写一次
- 各端决定自己启用哪些模块
- 平台专属内容天然分开
- 不需要到处写平台判断

## 推荐的模块契约

建议给 `packages/modules` 里的每个模块定义统一契约。这里的“模块”指独立 workspace 包。

可以是类似下面的结构：

```ts
export interface AppModule {
  id: string
  routes?: RouteRecordRaw[]
  install?: (context: AppModuleContext) => void | Promise<void>
  navItems?: AppNavItem[]
  requires?: PlatformCapabilityKey[]
}
```

其中：

- `id` 用于唯一标识
- `routes` 用于向应用注入路由
- `install` 用于注册 store、副作用、初始化逻辑
- `navItems` 用于把导航定义也模块化
- `requires` 用于声明依赖的平台能力

然后在应用启动时：

1. 创建平台能力上下文
2. 注册模块清单
3. 过滤掉能力不满足的模块
4. 汇总模块路由
5. 执行模块安装逻辑

这样后面新增手机课程表、桌面本地 AI、云端轮播图都很顺手。

## 平台能力注入方式

建议不要在模块里直接写：

- `import { xxx } from 'electron'`
- `import { StatusBar } from '@capacitor/status-bar'`
- `if (isPhone()) ...`

应该改成统一从平台上下文拿能力。

例如：

```ts
export interface PlatformCapabilities {
  authSession: AuthSessionCapability
  storage: StorageCapability
  theme: ThemeCapability
  localAi?: LocalAiCapability
  schedule?: ScheduleCapability
  bannerAdmin?: BannerAdminCapability
}
```

平台侧分别提供实现：

- 手机端提供 `schedule`
- 桌面端提供 `localAi`
- 云端提供 `bannerAdmin`

这样模块里只管“要什么能力”，不管“能力从哪来”。

## 哪些内容应该进入 `packages/modules`

推荐优先进入共享模块的内容：

- `auth`
- `todos`
- `profile`
- `system settings`
- 后续如果手机和云端都要用课程表，再考虑 `calendar`

这些模块的共同特点是：

- 业务含义稳定
- 三端复用概率高
- 与平台差异关系不大

## 哪些内容先不要进入 `packages/modules`

下面这些先保留在应用侧更合适：

- 云端博客首页整体展示
- 云端后台根布局
- 手机端底部导航壳
- 桌面端工作台首页
- 桌面本地 AI 工具台
- 手机端本地课程表首页

原因不是它们不能模块化，而是它们当前更像“产品壳层内容”，不是“稳定的跨端业务模块”。

## 结合当前仓库的迁移建议

### 第一阶段：先统一基础层

优先处理重复最明显的内容：

- 统一 `api` 访问入口，尽量让云端前端也完全对齐 `packages/api`
- 统一认证 store，尽量让云端前端也完全对齐 `packages/domain/auth`
- 统一主题状态模型，尽量三端都只走 `packages/theme`
- 抽出公共 bootstrap 流程到 `packages/app-core`

这一阶段完成后，三端的基础设施层会明显收敛。

### 第二阶段：抽共享模块

建议按下面顺序迁移：

1. `auth`
2. `profile`
3. `todos`

原因：

- 当前三端都已经有这几类能力或即将有这几类能力
- 逻辑稳定
- 抽出来以后收益最直接

### 第三阶段：补平台能力层

重点把差异明确化，而不是藏在业务代码里。

建议先抽这些能力：

- 认证会话驱动
- 本地存储驱动
- 系统主题驱动
- 文件系统驱动

后续再扩展：

- 本地 AI 驱动
- 课程表驱动
- 轮播图配置驱动

### 第四阶段：再处理复杂模块

后面再看是否要继续提炼：

- `blog`
- `files`
- `calendar`
- `local-ai`

这几块体量大、差异多，适合在前面几层稳定以后再动。

## 路由组织建议

路由建议改成“应用汇总模块路由”，不是“应用自己手写全部业务路由”。

例如：

```ts
const router = createRouter({
  history: createWebHistory(),
  routes: [
    ...collectModuleRoutes(appModules),
    ...appSpecificRoutes,
  ],
})
```

其中：

- 业务路由来自模块
- 404、根重定向、根布局等应用级路由来自 `apps/*`

这样边界会更清楚。

## 布局组织建议

布局不要抽成一份公共总布局。

推荐做法是：

- `packages/modules` 只输出页面内容和必要组件
- 根布局继续放在 `apps/*`
- 应用决定页面嵌在什么壳里

例如：

- 手机端继续自己的 tab 壳
- 桌面端继续自己的工作台壳
- 云端继续博客布局和后台布局分离

这是这套方案能长期稳定的关键。

## 对你这个项目最重要的几条边界

### 第一条：模块统一，不等于页面完全统一

统一的重点是：

- 数据模型
- store
- 接口调用
- 表单逻辑
- 列表逻辑
- 页面主体组件

不一定非要统一：

- 页面外壳
- 导航入口
- 动效
- 布局结构

### 第二条：平台差异要显式注入，不要隐式散落

不要让公共模块偷偷依赖：

- Tauri
- Capacitor
- 浏览器专属 API

应该让这些依赖都通过 `packages/platform` 暴露。

### 第三条：单端专属内容不要急着抽

例如：

- 云端轮播图后台
- 桌面端本地 AI
- 手机端课程表

这些都可以是模块，但前提是你已经确认它们未来至少会复用一部分，或者它们内部已经足够稳定。

如果现在还在频繁变形，先留在应用侧更稳。

## 推荐实施顺序

如果要控制改造风险，建议按下面顺序推进：

1. 先统一 `api`、`domain`、`theme`
2. 新建 `packages/app-core`
3. 抽 `auth` 模块
4. 抽 `profile` 模块
5. 抽 `todos` 模块
6. 建立 `packages/platform` 的能力接口
7. 最后再处理 `blog`、`files`、`calendar`、`local-ai`

这样做能保证你每一步都有明确收益，而且不需要一次性重写三端。

## 一句话总结

推荐架构是：

- 用 `packages/modules` 统一前端业务模块分组
- 用 `@personal-system/module-*` 作为应用侧稳定导入入口
- 用 `packages/platform` 承接平台差异
- 用 `apps/*` 保留各端壳层与独有能力
- 用 `packages/app-core` 收敛重复装配逻辑

这样既能减少云端、桌面端、手机端重复写，又不会把三端硬拧成一套后期难维护的结构。
