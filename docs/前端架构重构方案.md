# 前端架构重构方案

## 1. 背景

当前前端已经从纯页面堆砌逐步演进出了 `features`、`stores`、`views`、`components`、`composables` 等目录，但边界仍然不统一：

- `views` 中存在多个超大页面，页面既承担界面展示，又承担大量业务编排和状态管理。
- `features` 只在部分模块中生效，很多模块仍然需要在 `views`、`stores`、`utils`、`components` 之间横跳。
- `stores` 中混合了全局状态与业务状态，导致业务能力没有真正收口到业务目录。
- 基础设施层存在反向依赖业务层的情况，例如接口层直接依赖业务 store。

继续在现结构上追加功能，短期可以继续写，长期会出现以下问题：

- 新功能落点不稳定，同类型代码会被放到不同目录。
- 页面文件越来越大，后续拆分成本更高。
- 业务之间的依赖方向不清晰，公共层容易被污染。
- 新增移动端、博客新栏目、后台新模块时，复用成本高。

本项目为自用项目，可以重构，不要求向前兼容。这里直接采用方案 2：`app + shared + modules`。

核心目标：

- `app` 只负责应用启动、路由注册、守卫、全局初始化。
- `shared` 只放跨业务复用代码，不允许直接承载具体业务规则。
- `modules` 按业务域组织，每个业务自己持有 `api`、`types`、`store`、`页面组件`、`局部编排逻辑`。
- 页面复杂度向业务模块内部下沉，避免继续堆在 `views` 顶层。

## 3. 当前问题定位

### 3.1 页面过大

目前已有多个超大页面：

- `src/views/dashboard/FilesPage.vue`
- `src/views/dashboard/CollectionsPage.vue`
- `src/views/dashboard/TodosPage.vue`
- `src/views/dashboard/BillsPage.vue`
- `src/views/dashboard/ArticleEditor.vue`

这类文件普遍同时承担：

- 页面状态
- 接口调用
- 多弹窗控制
- 交互编排
- 列表展示
- 页面私有组件装配

这说明页面层过厚，应该继续向业务模块内拆分。

### 3.2 业务代码分散

以待办为例，当前代码分散在多个位置：

- 页面：`src/views/dashboard/TodosPage.vue`
- 业务接口：`src/features/todos/api.ts`
- 页面局部逻辑：`src/features/todos/page-*.ts`
- 状态：`src/stores/todo.ts`
- 表单工具：`src/utils/todoForm.ts`
- 组件：`src/views/dashboard/components/Todo*.vue`

一个模块跨越太多顶层目录，后续新增功能时很容易不知道该放哪里。

### 3.3 基础设施层反向依赖业务层

当前 `src/utils/api.ts` 中直接引用了：

- `src/stores/auth.ts`
- `src/stores/api-environment.ts`

这会导致公共接口层和业务状态层互相耦合，后续拆模块时很难保持依赖方向单一。

### 3.4 路由文件承担过多职责

当前 `src/router/index.ts` 同时负责：

- 全部路由定义
- 路由懒加载入口
- 认证恢复
- 权限守卫

随着后台模块继续增加，这个文件会持续膨胀。

## 4. 目录职责约束

### 4.1 `app`

只允许放：

- 应用启动
- 路由注册
- 路由守卫
- 全局初始化
- 与平台启动强相关的壳层逻辑

不允许放：

- 具体业务接口
- 具体业务页面实现
- 具体业务 store

### 4.2 `shared`

只允许放真正跨业务复用的能力：

- 通用接口客户端
- 通用错误处理
- 通用基础组件
- 通用 hooks
- 少量全局基础状态
- 全局样式与设计 token
- 纯工具函数

进入 `shared` 的判断标准：

- 至少被两个业务域复用，或者明确具备跨业务稳定复用价值。
- 不依赖任何具体业务模块。

不满足以上条件的代码，不要提前抽到 `shared`。

### 4.3 `modules`

每个业务模块自行拥有：

- `api.ts`
- `types.ts`
- `store.ts` 或 `model/`
- 页面组件
- 页面局部 composables
- 业务工具

业务模块之间允许通过明确出口进行依赖，但禁止随意穿透内部目录。

### 4.4 全局状态原则

重构后仅保留少量真正全局的状态：

- 认证
- 主题
- 设置
- API 环境

其中主题、设置、API 环境这类不承载具体业务规则的全局基础状态，统一收口到 `src/shared/stores`。

其他业务状态优先放回各自模块内，例如：

- `todo` store 下沉到 `modules/todos/store.ts`
- `moment` store 下沉到 `modules/moments/store.ts`
- `article-taxonomy` 优先归入 `modules/articles` 或 `modules/blog`

## 5. 目标映射

以下是当前目录向目标目录的迁移方向。

### 5.1 启动与路由

- `src/app/bootstrap.ts` 保留并归入 `src/app/bootstrap/`
- `src/router/index.ts` 迁移到 `src/app/router/index.ts`
- 新增：
  - `src/app/router/blog.routes.ts`
  - `src/app/router/dashboard.routes.ts`
  - `src/app/router/guards.ts`

### 5.2 通用层

- `src/utils/api.ts` -> `src/shared/api/client.ts`
- `src/components` 中真正通用的组件 -> `src/shared/components`
- `src/composables` 中真正通用的 composable -> `src/shared/composables`
- `src/constants` -> `src/shared/constants`
- `src/styles` -> `src/shared/styles`
- `src/types` -> `src/shared/types`
- `src/utils` 中纯工具函数 -> `src/shared/utils`

注意：只迁移真正通用的部分，业务专属工具不要硬塞进 `shared`。

### 5.3 业务层

建议的优先映射如下。

## 6. 导入规则

重构后应遵守以下依赖方向：

```text
app -> modules / shared
modules -> shared
shared -> 不依赖 modules
```

禁止出现：

- `shared` 反向依赖 `modules`
- 一个业务模块直接读取另一个业务模块的内部实现文件
- 页面层直接从多个顶层目录随意拼装零散逻辑

推荐做法：

- 跨模块调用只通过公开出口文件进行
- 模块内部组件优先使用相对路径
- 模块外部调用模块能力时，尽量从模块根导出

## 7. 页面拆分原则

对于 800 行以上页面，默认进入拆分名单。

拆分顺序：

1. 先拆接口与数据编排
2. 再拆页面局部 composable
3. 再拆对话框与复杂列表组件
4. 最后清理样式和重复逻辑

页面最终建议只保留：

- 页面级路由参数读取
- 页面级布局装配
- 少量页面级状态协调

不建议页面继续直接持有：

- 大量接口调用细节
- 超长表单数据转换
- 大量批处理逻辑
- 多种弹窗状态机

## 9. 验收标准

每个阶段完成后，至少满足以下条件：

- 新增代码已经落入 `app / shared / modules` 目标结构
- 业务模块的接口、类型、状态、页面局部逻辑基本收口
- `shared` 不依赖业务模块
- 页面文件体积明显下降
- 旧目录中的重复实现没有继续增长
- 前端通过 `lint`
- 前端通过 `typecheck`

## 11. 执行约定

后续重构默认遵守以下约定：

- 先迁目录和依赖方向，再做业务细拆。
- 优先做“收口”，暂时不追求一步到位的完美抽象。
- 没有明确复用价值的代码，不提前进入 `shared`。
- 不为旧目录保留长期兼容层，迁完即可直接改引用。
- 每完成一个阶段，都执行前端 `lint` 与 `typecheck`。
