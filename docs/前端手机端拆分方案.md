# 前端手机端拆分方案

## 结论

手机端不要从 `apps/cloud/frontend` 直接复制一份到 `apps/phone`，而是采用“两个应用壳 + 一套共享业务层”的拆分方式：

- `apps/cloud/frontend` 保留为 Web 前端，继续承载博客、工具页、控制台
- `apps/phone` 新建为独立手机端应用，负责移动端信息架构、底部导航、原生壳能力
- 共享内容优先下沉到 `packages/*`，先共享 API、类型、业务逻辑，再按需共享小型通用组件

这一方案的目标不是“把响应式页面挪过去”，而是把手机端从当前大一统前端中彻底解耦出来。

## 当前现状

当前 `apps/cloud/frontend` 已经同时承载了多种职责：

- Web 博客页面
- Web 工具页
- Web 控制台页面
- 移动端响应式布局
- Capacitor 原生壳接入
- Android 工程目录

从代码结构看，几个关键耦合点如下：

- [apps/cloud/frontend/src/app/router/index.ts](../apps/cloud/frontend/src/app/router/index.ts) 同时注册了博客、工具、控制台三套路由
- [apps/cloud/frontend/src/App.vue](../apps/cloud/frontend/src/App.vue) 把头部、登录弹窗、浮动按钮、页面特效统一挂在同一个应用壳上
- [apps/cloud/frontend/src/modules/blog/pages/BlogHome.vue](../apps/cloud/frontend/src/modules/blog/pages/BlogHome.vue) 内部已经混合了桌面侧栏布局和移动端底部组件
- [apps/cloud/frontend/src/app/native-shell.ts](../apps/cloud/frontend/src/app/native-shell.ts) 把 Capacitor 原生行为直接绑在当前前端应用初始化流程中
- [apps/cloud/frontend/src/shared/api/runtime.ts](../apps/cloud/frontend/src/shared/api/runtime.ts) 内部已经包含 Web 与原生端 API 地址解析逻辑

这说明现在的主要问题不是“有没有手机端样式”，而是“一个前端应用同时承担了 Web 和 App 两套产品边界”。

## 不建议直接复制的原因

如果把 `apps/cloud/frontend` 直接复制到 `apps/phone`，短期看似快，后续会立刻出现几个问题：

1. 业务逻辑双份维护
   - `api.ts`、`types.ts`、`store`、`helper` 很快会出现两份
   - 一个接口字段变化后，需要手工改两边

2. UI 结构继续互相污染
   - 手机端会被继承大量桌面布局、博客头部、控制台菜单、工具页逻辑
   - 后续裁剪成本高于一开始重新组织边界

3. Capacitor 与 Web 构建继续混在一起
   - `android/`、`capacitor.config.ts`、移动端环境变量会继续留在 Web 前端目录内
   - Web 端和手机端构建链难以独立演进

4. 后续重构阻力更大
   - 两边看起来分开，实际上共享方式靠复制粘贴
   - 一旦页面差异逐步扩大，最终会进入不可控分叉

## 推荐目标结构

建议演进到下面这个结构：

```text
apps/
  cloud/
    backend/
    frontend/             # 纯 Web 前端
  phone/                  # 纯手机端应用

packages/
  api/                    # axios、运行时环境、接口客户端
  domain/                 # types、业务 helper、可复用 store
  ui-shared/              # 真正轻量且跨端稳定的小组件
```

如果暂时不想引入完整 monorepo 工具链，也可以先只做目录级拆分，再通过 TypeScript 路径别名或工作区依赖引用共享包。

## 拆分原则

### 1. 先抽无界面共享层，不先抽页面

优先下沉的内容：

- `shared/api/*`
- `modules/*/api.ts`
- `modules/*/types.ts`
- 与界面无关的 `helper`
- 与具体布局弱耦合的 `store`

暂时不要强行共享的内容：

- `App.vue`
- `AppHeader.vue`
- `DashboardLayout.vue`
- `BlogHome.vue`
- 大型控制台页面
- 重桌面交互组件

原因很直接：业务逻辑复用的边界稳定，页面复用的边界不稳定。过早共享页面，只会把 `apps/phone` 再次拖回统一前端结构。

### 2. 手机端是独立产品，不是当前前端的一个样式分支

`apps/phone` 应该按手机使用路径重新设计路由和导航，而不是继续复用 Web 控制台的信息架构。

例如手机端更适合：

- 底部 Tab
- 单列页面流
- 局部抽屉与全屏面板
- 面向高频操作的首页聚合

而不是继续保留：

- 桌面侧边栏控制台
- 大量并排卡片
- 重编辑器页面
- 复杂多栏博客首页

### 3. 共享业务，不共享产品壳

Web 和手机端可以共享：

- 登录态恢复逻辑
- API 客户端
- 数据模型
- 业务校验与转换函数
- Todo、Bills、Moments 等模块的核心状态逻辑

Web 和手机端不应强绑共享：

- 根组件
- 路由树
- 布局组件
- 导航组件
- 页面级视觉结构

## 建议的首批共享范围

首批最值得抽出的共享模块如下：

### API 层

- `apps/cloud/frontend/src/shared/api/client.ts`
- `apps/cloud/frontend/src/shared/api/context.ts`
- `apps/cloud/frontend/src/shared/api/errors.ts`
- `apps/cloud/frontend/src/shared/api/index.ts`
- `apps/cloud/frontend/src/shared/api/runtime.ts`

这里建议整理成 `packages/api`，统一负责：

- `axios` 实例
- API base URL 解析
- 未授权处理
- 环境切换逻辑
- 各业务接口导出

### 业务模型层

建议优先抽出这些模块中的 `types`、`api`、`helper`、`store`：

- `auth`
- `todos`
- `bills`
- `moments`
- `system`

其中 `todos` 是最适合先拆的模块，因为它已经有比较完整的业务模型与状态逻辑，但页面层与业务层还能明显区分。

### 通用状态层

可评估下沉的 store：

- 主题
- 设置
- 鉴权
- API 环境

但要注意：如果某个 store 内部依赖了当前 Web 页面结构、弹窗行为、路由跳转细节，就先不要直接复用到手机端，应该先切出纯状态部分。

## 建议的手机端首批范围

`apps/phone` 第一阶段只做高频、适合手机端的能力，不要一上来追求“全部可用”。

建议优先迁入：

1. 登录
2. 首页聚合
3. 待办
4. 账单
5. 动态
6. 我的

视情况再跟进：

1. 文件上传
2. 收藏收纳库的移动端只读或轻编辑能力

不建议首批迁入：

1. 博客首页整套视觉系统
2. 工具页
3. 文章编辑器
4. 文件管理器完整桌面能力
5. 管理后台大部分页面

这些内容要么明显偏 Web，要么交互复杂度高，不适合成为手机端拆分的第一阶段目标。

## 分阶段执行方案

### 第一阶段：清理现有前端边界

目标：不新建手机页面，只把共享层边界先挖出来。

建议任务：

1. 识别 `apps/cloud/frontend` 中哪些文件属于应用壳，哪些属于业务共享层
2. 抽出 `shared/api` 到 `packages/api`
3. 抽出 `auth`、`todos`、`bills`、`moments` 的 `types/api/helper/store` 到 `packages/domain`
4. 调整 `apps/cloud/frontend` 引用，改为依赖共享包
5. 保证 Web 前端行为不变

这一阶段完成后，Web 前端仍然只有一个，但“共享业务层”已经从原目录中解耦。

### 第二阶段：创建 `apps/phone`

目标：建立独立手机端壳，不复用 Web 根组件和路由结构。

建议任务：

1. 新建 `apps/phone`
2. 独立配置 `package.json`
3. 独立配置 `vite.config.ts`
4. 独立配置 `capacitor.config.ts`
5. 将 `android/` 迁移或新建到 `apps/phone`
6. 建立手机端专用路由、底部 Tab、页面容器
7. 接入 `packages/api` 与 `packages/domain`

这一阶段结束后，手机端即使页面很少，也应该已经是一个独立应用，而不是 Web 前端的别名入口。

### 第三阶段：按模块迁移页面

目标：按业务优先级逐步落地手机页面。

建议顺序：

1. `auth`
2. `todos`
3. `bills`
4. `moments`
5. `files` 的必要移动能力

迁移时的原则：

- 页面重写可以接受
- 业务逻辑尽量复用
- 不为了复用页面而牺牲手机端结构

### 第四阶段：回收 Web 端内的移动专属逻辑

当 `apps/phone` 稳定后，再逐步从 `apps/cloud/frontend` 删除这些内容：

- 仅服务原生壳的逻辑
- 仅服务手机端的特殊环境变量
- 仅服务移动端入口的构建脚本
- 已不再需要的响应式妥协代码

这样 Web 前端会重新回到“纯 Web”职责，目录会明显更干净。

## 页面与模块的边界建议

为了避免后续再次耦合，建议今后按下面的边界组织代码：

### `apps/cloud/frontend`

只保留：

- Web 路由
- Web 布局
- Web 页面
- Web 专属视觉组件

### `apps/phone`

只保留：

- 手机端路由
- 原生壳能力接入
- 手机端页面
- 手机端导航与交互容器

### `packages/api`

只保留：

- HTTP 客户端
- API 环境
- 接口封装
- 认证上下文协作

### `packages/domain`

只保留：

- 类型
- 领域模型
- 业务转换
- 纯业务 store
- 与平台无关的 helper

### `packages/ui-shared`

只保留真正稳定的跨端小组件，例如：

- 标签输入
- 通用确认框壳
- 空状态
- 小型表单片段

这里一定要克制，不要把页面骨架、导航条、布局容器也塞进去。

## 实施时的注意事项

1. 不要先动博客首页
   - [apps/cloud/frontend/src/modules/blog/pages/BlogHome.vue](../apps/cloud/frontend/src/modules/blog/pages/BlogHome.vue) 现在同时承担视觉、布局、内容编排、移动端适配，拆它的收益最低，风险最高

2. 不要先共享大页面组件
   - 共享大组件通常会把路由、布局、弹窗、样式策略一起绑定过去，后面更难拆

3. 先让 Web 依赖共享包，再让手机端接入
   - 这样共享层是否稳定，可以先在现有前端里得到验证

4. Capacitor 应尽量收敛到 `apps/phone`
   - 原生返回键、状态栏、键盘适配等都更适合作为手机端应用壳职责

5. 接受手机端页面重写
   - 对手机端来说，重写页面通常比从桌面页面里裁出一版更便宜

## 推荐的下一步

建议按下面顺序继续推进：

1. 先整理共享层目录方案
2. 先抽 `shared/api`
3. 再抽 `todos` 与 `auth`
4. 让 `apps/cloud/frontend` 先跑在新结构上
5. 再创建 `apps/phone` 并接入共享层

如果进入实际重构阶段，第一步最适合做的是：

- 新建 `packages/api`
- 新建 `packages/domain`
- 把 `shared/api` 和 `todos/auth` 的纯业务部分先迁过去

这样风险最小，也最容易验证拆分路径是否正确。
