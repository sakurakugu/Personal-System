# 桌面端与桌面小工具方案

## 结论

当前项目后续如果同时扩展“电脑端独立应用”和“桌面小工具”，推荐采用下面这套方案：

- Web 电脑端继续保留现有 `apps/cloud/frontend`
- 独立电脑端优先采用 `Tauri + 现有 Vue 前端`
- 桌面小工具采用 `Qt`
- 认证体系保持统一
- 会话载体分开
  - 浏览器与 WebView：`Cookie Session + CSRF`
  - 原生客户端与小工具：`设备令牌`
- 当前阶段不建议把整个系统全面改成 JWT

这套方案的核心不是“所有端都用同一种登录凭证”，而是“所有端都遵守同一套用户、权限、设备管理规则，再根据客户端能力选择合适的会话载体”。

## 当前基础判断

从现有仓库结构和实现看，当前认证体系本质上已经是浏览器会话模型：

- 前端共享认证状态逻辑位于 `packages/domain/src/auth/store.ts`
- 前端共享接口客户端位于 `packages/api/src/client.ts`
- 后端登录与登出入口位于 `apps/cloud/backend/app/modules/auth/api.py`
- 后端会话 Cookie 处理位于 `apps/cloud/backend/app/modules/auth/cookies.py`
- 后端 Session 存储位于 `apps/cloud/backend/app/modules/auth/sessions.py`

当前机制的关键点如下：

- 登录成功后，后端写入 `session_id` 与 `csrf_token`
- 前端通过 `withCredentials` 自动带 Cookie
- 写操作自动附带 `X-CSRF-Token`
- 服务端 Session 存储在 Redis

这说明当前系统更接近“服务端 Session 站点”，而不是“前后端完全分离 JWT 站点”。

## 为什么不建议统一成一种会话载体

这里要先区分两个概念：

### 应该统一的部分

- 用户体系
- 权限模型
- 设备管理
- 过期策略
- 吊销策略
- 登录审计

### 不应该强行统一的部分

- 浏览器 Cookie
- 原生客户端 Token
- 小工具专用轻权限凭证

原因很直接：

- 浏览器天然适合 `Cookie Session`
- Qt 小工具天然更适合 `Token`
- 如果强行让桌面小工具复用浏览器 Cookie，会增加 Cookie 容器管理、跨进程共享、CSRF、会话同步的复杂度
- 如果强行让整个系统统一改成 JWT，则会把当前已经稳定工作的 Web 登录模型一起推翻，收益不高

所以真正正确的统一方式，是统一认证内核，而不是统一登录载体。

## 桌面端技术路线判断

当前可选方向本质上有三种。

### 方案一：`Tauri + 现有 Vue 前端`

这是当前最推荐的主电脑端方案。

优点：

- 最大化复用现有 `apps/cloud/frontend`
- 复用现有 Vue、Vite、Element Plus、Pinia、Vue Router 资产
- 桌面应用体积相对更小
- 后续托盘、通知、开机自启、本地文件桥接也能逐步补

缺点：

- 仍然是 Web 技术栈渲染
- 如果未来强烈追求原生桌面视觉，需要额外投入

适用前提：

- 目标是尽快落地独立桌面端
- 目标是优先复用现有前端能力

### 方案二：纯 `Qt / QML` 桌面端

这是长期原生化方向，但不是当前最省力的方案。

优点：

- 原生桌面能力更强
- 与桌面小工具技术栈统一
- 对系统集成、常驻、透明窗口、悬浮、原生体验更友好

缺点：

- 需要重写主界面
- 现有前端页面资产复用率低
- 首次建设成本明显更高

适用前提：

- 明确要做长期原生桌面产品
- 可以接受额外建设周期

### 方案三：`Qt + Web`

当前不推荐作为主路线。

问题不在于它不能做，而在于它通常会同时承受两边成本：

- 仍然要维护 Web UI
- 还要处理 Qt 壳层
- 主程序与小工具未必真的能共享大部分界面代码
- 后续很容易处于“暂时先这样”的中间态，最后再拆一次

如果只是为了尽快做桌面端，`Tauri` 更直接；如果是为了原生化，纯 `Qt` 更彻底。`Qt + Web` 的定位最尴尬。

## 推荐组合

结合当前仓库现状，建议采用下面的组合：

### 主电脑端

- 采用 `Tauri + apps/cloud/frontend`
- 把它视为“独立桌面壳”，不是再新做一套桌面前端

### 桌面小工具

- 采用 `Qt`
- 按独立小程序思路建设
- 只展示高频轻量信息

### Web 端

- 保持现有 `apps/cloud/frontend`
- 继续作为浏览器端主入口

这样拆的好处是：

- 主程序尽量复用现有前端资产
- 小工具走最适合桌面原生常驻场景的技术栈
- 两者不互相绑架

## 认证方案推荐

推荐把认证体系拆成“统一认证内核 + 两类会话载体”。

### 一、浏览器与 WebView

继续保留现有：

- `Cookie Session`
- `CSRF`
- Redis 服务端 Session

适用对象：

- `apps/cloud/frontend`
- 当前 `apps/phone`
- 未来任何基于浏览器上下文、且 Cookie 行为稳定的壳

### 二、原生客户端与桌面小工具

新增：

- `设备令牌`

这里的“设备令牌”建议优先理解为：

- 服务端可查询
- 服务端可吊销
- 支持过期时间
- 支持刷新或重新签发
- 可记录设备名、设备类型、最后使用时间

它不一定必须是 JWT，也可以是数据库或 Redis 可查的随机字符串凭证。

适用对象：

- 未来 Qt 桌面端
- Qt 桌面小工具
- 后续如果手机端原生能力增强，也可以迁入

## 为什么当前不建议全面改 JWT

JWT 不是不能用，而是当前项目没有足够理由把它作为全局主认证方式。

### 当前不明显需要 JWT 的原因

- 现在已经有稳定的服务端 Session 体系
- 当前后端是单体主服务，不是多微服务独立验签体系
- 设备吊销在服务端 Session / 设备令牌模型下更直接
- 小工具一旦泄漏长期 JWT，控制面反而更差

### JWT 更适合的场景

- 多服务独立验签
- 第三方外部接入
- 明确需要无状态验签
- 有统一身份服务与较复杂的跨系统授权边界

如果未来演进到这些场景，再引入 JWT 更合适；当前阶段不值得为了“听起来统一”而整体切换。

## 推荐的设备令牌模型

原生端建议采用“设备会话”思路，而不是单个永久 Token。

### 设备会话建议具备的字段

- `id`
- `user_id`
- `device_name`
- `device_type`
- `token_hash`
- `expires_at`
- `last_used_at`
- `created_at`
- `revoked_at`

### 推荐能力

- 登录时创建设备会话
- 客户端本地只保存原始令牌
- 服务端只保存哈希值
- 支持查看当前账号下所有设备
- 支持单设备下线
- 支持全设备下线

### 对桌面小工具的额外约束

桌面小工具不建议直接复用主桌面端完整登录态。

更合适的方式是：

- 小工具使用单独设备令牌或专用轻权限令牌
- 权限限制为少量高频接口
- 不直接给管理后台、用户资料编辑、敏感操作权限

这样即使小工具侧凭证泄漏，影响面也更小。

## 对桌面小工具的职责边界建议

桌面小工具不要做成“缩小版完整系统”，而应该只承载高频、低风险、低认知负担的能力。

建议优先承载：

- 今日待办
- 快速新增待办
- 最近账单摘要
- 提醒与计数
- 系统状态摘要

不建议首批承载：

- 后台管理
- 文章编辑
- 文件管理器完整能力
- 高风险账户操作

这会直接影响认证设计：小工具越轻，越应该采用更小权限范围的专用凭证。

## 目录级落位建议

### 后端

建议在 `apps/cloud/backend/app/modules/auth/` 继续扩展，而不是另起一套完全平行的认证系统。

可新增的方向：

- `device_tokens.py` 或 `device_sessions.py`
- `device_api.py`
- `device_schemas.py`
- `device_service.py`

建议新增的能力：

- 原生端登录
- 刷新令牌或续期
- 查询当前账号设备列表
- 吊销指定设备

### 共享前端层

当前 `packages/domain/src/auth/store.ts` 假设主要是浏览器会话恢复。

后续建议抽象出“认证驱动”概念，例如：

- 浏览器会话驱动
- 原生设备令牌驱动

但 `store` 本身仍然保持统一入口，这样前端业务层不需要到处分支。

### API 层

当前 `packages/api/src/client.ts` 主要围绕 Cookie 工作。

后续建议扩展为：

- 浏览器模式：继续 `withCredentials + CSRF`
- 原生模式：附带 `Authorization` 请求头

这里是扩展，不是推翻。

### 桌面小工具

如果未来新增独立目录，建议把它视为独立产品边界，不直接塞进现有前端目录中。

例如可以采用：

```text
apps/
  cloud/
    backend/
    frontend/
  phone/
  desktop/
  desktop-widget/
```

其中：

- `desktop/` 用于独立电脑端
- `desktop-widget/` 用于 Qt 小工具

是否最终采用这两个目录名可以再定，但产品边界建议从一开始就分开。

## 分阶段实施建议

### 第一阶段：不改现有 Web 登录方式

目标：

- 不破坏当前浏览器与手机端登录行为
- 先把认证设计边界理顺

任务：

- 保持当前 `Cookie Session + CSRF`
- 设计设备令牌数据模型
- 设计设备管理接口

### 第二阶段：后端补设备令牌能力

目标：

- 为原生客户端准备独立会话能力

任务：

- 新建设备会话模型
- 新增设备登录接口
- 新增设备查询与吊销接口
- 接入现有用户与权限体系

### 第三阶段：建设独立电脑端

推荐优先路线：

- 先做 `Tauri + 现有 Vue 前端`

任务：

- 评估哪些页面直接复用
- 评估哪些桌面能力需要额外桥接
- 让独立电脑端走设备令牌或独立原生登录流程

### 第四阶段：建设 Qt 小工具

目标：

- 做高频轻量入口

任务：

- 收敛小工具范围
- 设计小工具专用接口
- 接入轻权限设备令牌

### 第五阶段：再决定手机端是否迁移

如果后续手机端需要更强原生能力，再评估是否从当前 Cookie 会话切换到设备令牌。

这一步不应提前做。

## 最终推荐决策

如果只保留最核心的决策，结论如下：

### 桌面端技术路线

- 主电脑端：优先 `Tauri + 现有 Vue`
- 桌面小工具：`Qt`
- 不推荐主路线采用 `Qt + Web`

### 认证路线

- 统一认证内核
- 不统一单一会话载体
- Web 继续 `Cookie Session + CSRF`
- 原生客户端与小工具采用 `设备令牌`
- 当前阶段不全面切换 JWT
