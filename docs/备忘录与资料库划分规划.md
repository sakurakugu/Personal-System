# 备忘录与资料库划分规划

## 背景

当前 `collections` 已经实现为“收藏收纳库”，承担了临时收纳、资料整理、附件关联和转文章 / 动态 / 待办的能力。

随着使用场景变多，单一“收藏收纳库”会同时承接两类不同内容：

- 临时记录：例如随手写一句话、微信复制一段内容、临时保存一个网址、还没有判断价值的想法。
- 长期资料：例如已经分类的网页、摘录、截图、文件、可复用参考资料。

这两类内容的使用心智不同：

- 临时记录需要极低录入成本，不应该要求标题、类型、标签、附件和分类。
- 长期资料需要可检索、可归类、可关联，应该保持结构清晰。

因此后续建议把产品心智调整为：

`备忘录负责待整理文本入口，资料库负责已归类长期资料。`

## 最终命名

推荐对外产品名：

- `备忘录`
- `资料库`

内部命名建议：

- 新增后端模块：`memos`
- 新增前端模块：`packages/modules/备忘录`
- 保留现有后端模块名：`collections`
- 保留现有数据表名前缀：`collections`
- 将现有“收藏收纳库”的界面文案逐步改为“资料库”

说明：

- `collections` 作为内部英文名仍然可接受，含义可以理解为资料集合。
- 第一阶段只改产品文案和导航名称，不强制迁移内部模块名，避免无意义的大范围重命名。

## 职责边界

### 备忘录

备忘录是快速文本入口，特点是：

- 只保存文本。
- 可以没有标题。
- 可以没有分类。
- 可以包含网址、摘录、想法、待办线索、文章灵感、微信复制内容。
- 默认处于待整理状态。
- 不支持附件。
- 不承担长期资料管理职责。

适合放入备忘录的内容：

- “微信看到一段话，先存着。”
- “突然想到一个文章标题。”
- “这个网址之后看看。”
- “某个事情好像要处理，先记一下。”
- “一段还没判断用途的复制文本。”

### 资料库

资料库是长期资料沉淀层，特点是：

- 保存已经确认有长期价值的资料。
- 支持标题、类型、正文、备注、标签、附件。
- 支持来源和分类。
- 支持检索、筛选、归档。
- 可以作为文章、动态、待办的参考来源。

适合放入资料库的内容：

- 已经分类的网页资料。
- 重要摘录。
- 可复用的写作素材。
- 截图和文件资料。
- 项目参考文档。
- 需要长期检索的外部信息。

### 文章、动态、待办、文件

- `articles`：正式长文、可发布内容、长期表达。
- `moments`：短表达、即时记录、动态展示。
- `todos`：行动项、提醒、任务。
- `files`：附件本体和文件管理。

备忘录和资料库都不是最终输出层，它们只负责承接和整理输入。

## 判断规则

判断一条内容应该进入哪里，可以按下面顺序：

1. 只是想先记下来，暂时不分类：放 `备忘录`。
2. 已经知道它是有价值资料，并且要长期检索：放 `资料库`。
3. 已经形成完整表达，准备作为长文维护：放 `文章`。
4. 只是想短句表达或发布近况：放 `动态`。
5. 需要行动、提醒或跟进：放 `待办`。
6. 只是保存文件本体：放 `文件`。

典型流程：

```text
临时文本 / 网址 / 摘录
  -> 备忘录
    -> 转资料库
    -> 转文章草稿
    -> 转动态草稿
    -> 转待办
    -> 归档 / 删除

已归类资料 / 截图 / 文件 / 重要摘录
  -> 资料库
    -> 转文章草稿
    -> 转动态草稿
    -> 转待办
    -> 归档 / 删除
```

## Obsidian 思路参考

Obsidian 的核心不是把内容放进很多重型模块，而是：

- `Vault`：一个本地资料库目录。
- `Markdown 文件`：每条笔记都是普通文本文件。
- `文件夹`：提供粗粒度分类。
- `标签`：提供横向分类。
- `双链`：用 `[[链接]]` 建立内容之间的关系。
- `属性`：用 frontmatter 保存结构化元数据。
- `视图`：通过搜索、图谱、插件或 Bases 从同一批笔记生成不同查看方式。

对当前系统的启发是：

- 不要让文章模块承接所有文字内容。
- 不要让资料库继续承担极低门槛收件箱。
- 用轻量备忘录承接“还没判断价值”的文本。
- 用资料库承接“已经决定保留并可检索”的资料。
- 后续如果需要知识图谱、双链、主题页，可以在资料库上扩展，而不是一开始就做完整知识库。

## 数据模型建议

### 备忘录 `memos`

第一版字段建议：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | UUID | 主键 |
| `user_id` | UUID | 所属用户 |
| `content` | text | 备忘录正文 |
| `status` | enum | 状态 |
| `source` | enum / string | 来源，可选 |
| `converted_to_type` | string | 已转出的目标类型，可选 |
| `converted_to_id` | UUID | 已转出的目标 ID，可选 |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 更新时间 |
| `archived_at` | datetime | 归档时间，可选 |
| `deleted_at` | datetime | 软删除时间，可选 |

状态建议：

| 状态 | 含义 |
| --- | --- |
| `inbox` | 待整理 |
| `processed` | 已处理 |
| `archived` | 已归档 |
| `dropped` | 废弃 |

来源建议：

| 来源 | 含义 |
| --- | --- |
| `manual` | 手动输入 |
| `wechat` | 微信复制 |
| `web` | 网页 |
| `share` | 系统分享 |
| `unknown` | 未知 |

第一版不建议加入：

- 附件。
- 独立标签体系。
- 分类树。
- 富文本。
- 复杂关联图。

避免备忘录演变成第二个资料库。

### 资料库 `collections`

现有 `collections` 可以继续使用，后续定位调整为资料库。

建议逐步补充或强化：

| 能力 | 说明 |
| --- | --- |
| 分类 | 用于资料主归属，可以后续新增单独分类表 |
| 标签 | 保留现有标签体系，负责横向索引 |
| 来源 | 记录网页、微信、截图、文件、手动等来源 |
| 关联对象 | 记录被哪个文章、动态、待办引用或转出 |
| 资料状态 | 从收纳状态逐步调整为资料维护状态 |

资料库状态可以沿用当前状态，但产品文案建议调整：

| 当前状态 | 资料库文案 |
| --- | --- |
| `inbox` | 待归类 |
| `processing` | 整理中 |
| `ready` | 已归类 |
| `archived` | 已归档 |
| `dropped` | 废弃 |

如果后续备忘录承担了主要待整理入口，可以逐渐减少资料库中 `inbox` 的使用。

## 转换能力

### 备忘录转资料库

规则：

- 备忘录正文写入资料库正文。
- 如果正文第一行较短，可作为资料标题候选。
- 识别到 URL 时，可以填充来源链接或正文。
- 转换成功后，备忘录标记为 `processed`。
- 保留 `converted_to_type = collection` 和 `converted_to_id`。

### 备忘录转文章草稿

规则：

- 备忘录正文写入文章正文。
- 第一行可作为文章标题候选。
- 文章状态为草稿。
- 转换成功后，备忘录标记为 `processed`。

### 备忘录转动态草稿

规则：

- 备忘录正文写入动态草稿。
- 如果已有动态草稿，需要弹窗确认追加、覆盖或取消。
- 转换成功后，备忘录标记为 `processed`。

### 备忘录转待办

规则：

- 第一行作为待办标题。
- 完整正文作为待办描述。
- 自动补充 `备忘录` 标签。
- 转换成功后，备忘录标记为 `processed`。

### 资料库转输出

保留现有能力：

- 资料库转文章草稿。
- 资料库转动态草稿。
- 资料库转待办。

后续可补充：

- 资料库关联已有文章。
- 资料库关联已有待办。
- 资料库记录引用历史。

## 页面设计建议

### 备忘录页面

第一版页面目标是快。

核心区域：

- 顶部快速输入框。
- 待整理列表。
- 已处理 / 归档筛选。
- 搜索。
- 单条展开编辑。
- 单条转资料库、转文章、转动态、转待办、归档、删除。

输入体验：

- 默认只需要一个多行文本框。
- 支持 `Ctrl + Enter` 保存。
- 保存后输入框清空并继续聚焦。
- 移动端优先支持快速输入。

列表展示：

- 显示正文前几行。
- 显示创建时间。
- 自动识别网址并可点击。
- 已转换内容显示目标类型。

### 资料库页面

现有收藏收纳库页面逐步调整：

- 菜单名改为 `资料库`。
- 页面标题改为 `资料库`。
- 新增按钮文案从 `新增收藏` 改为 `新增资料`。
- 列表空状态改为资料库语义。
- 筛选区突出分类、标签、类型、状态。
- 转出动作保留。

资料库新增内容时，不再强调“随手存一下”，而是强调“录入一条可长期保留的资料”。

| 备忘录 | `/dashboard/memos` | `/memos` | `/memos` |

- 桌面端可以放在主导航或工具入口中。

## 迁移策略

不建议自动把现有收藏数据迁移到备忘录。

原因：

- 现有 `collections` 已经有附件、标签、状态和转出能力。
- 很难准确判断哪些是临时备忘，哪些是长期资料。
- 自动迁移可能破坏现有资料结构。

推荐策略：

1. 保留现有收藏数据在 `collections`。
2. 界面文案改为资料库。
3. 新增备忘录后，新的临时文本默认进入备忘录。
4. 需要清理旧数据时，在资料库中手动归档或重分类。

## 验收标准

第一版完成后应满足：

- 可以在管理端快速创建一条纯文本备忘录。
- 可以查看待整理备忘录列表。
- 可以编辑、归档、软删除备忘录。
- 可以把备忘录转为资料库资料。
- 可以把备忘录转为文章草稿。
- 可以把备忘录转为待办。
- 资料库界面文案不再强调“收藏收纳库”，而是体现长期资料库定位。
- 旧的资料库转文章、转动态、转待办能力不受影响。

## 暂不实现

第一版暂不做：

- 富文本编辑。
- 附件上传。
- 标签体系。
- 分类树。
- 双链。
- 图谱。
- 自动网页抓取。
- 自动 OCR。
- AI 自动整理。
- 浏览器插件。

这些能力可以后续围绕资料库扩展，而不是压到备忘录里。

## 最终结论

后续推荐采用：

```text
备忘录 = 待整理文本入口
资料库 = 已归类长期资料
文章 = 长文输出
动态 = 短表达输出
待办 = 行动输出
文件 = 附件本体
```

这样可以同时保留低门槛记录体验和干净的资料库结构。
