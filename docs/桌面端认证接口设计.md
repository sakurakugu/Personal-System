# 桌面端认证接口设计

## 目标

这份文档用于把“桌面端与桌面小工具采用独立设备认证”的方案落到可实现层面。

当前目标不是重写全站认证，而是在保留现有 Web 认证方式的前提下，为下面两类客户端补充可落地的原生认证能力：

- 独立桌面端
- 桌面小工具

## 设计结论

### 保留的现有方案

浏览器端继续沿用当前方案：

- `Cookie Session`
- `CSRF`
- Redis 服务端 Session

适用对象：

- `apps/cloud/frontend`
- 当前 `apps/phone`

### 新增方案

原生客户端新增：

- `设备会话令牌`

适用对象：

- 未来 `desktop`
- 未来 `desktop-widget`

### 明确不采用的方案

当前阶段不采用：

- 全站统一 JWT
- 桌面小工具复用浏览器 Cookie
- 主桌面端与小工具共用同一长期全权限凭证

## 为什么选择“设备会话令牌”

这里采用的不是 JWT，而是“服务端可追踪、可吊销的不透明令牌”。

它的特点是：

- 客户端拿到的是随机字符串
- 服务端只保存哈希值
- 服务端可以随时吊销
- 服务端可以记录设备名、设备类型、权限范围、最后使用时间
- 服务端可以直接列出当前账号所有设备

这比 JWT 更符合当前项目：

- 后端当前已经是服务端会话思路
- 需要设备管理
- 需要小工具轻权限能力
- 不需要多服务无状态验签

## 会话模型选择

当前推荐第一阶段采用：

- 单设备会话
- 单不透明令牌
- 服务端过期控制
- 可选滑动续期

不在第一阶段引入：

- `access token + refresh token` 双令牌体系

原因：

- 当前项目是单体后端
- 桌面端和小工具数量有限
- 单令牌实现更直接
- 吊销和设备管理更简单

如果未来出现更复杂的跨端长期在线需求，再升级为双令牌体系即可。

## 客户端认证矩阵

| 客户端 | 会话方式 | 请求凭证 | 是否需要 CSRF | 备注 |
| --- | --- | --- | --- | --- |
| Web 浏览器 | Cookie Session | Cookie | 是 | 保持现状 |
| 手机端当前实现 | Cookie Session | Cookie | 是 | 保持现状 |
| 独立桌面端 | 设备会话令牌 | `Authorization: Bearer ...` | 否 | 新增 |
| 桌面小工具 | 设备会话令牌 | `Authorization: Bearer ...` | 否 | 新增 |

## 令牌格式建议

建议客户端拿到的原始令牌格式如下：

```text
pst_dev_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

设计原则：

- 带固定前缀，便于日志和调试识别
- 原始值长度足够长
- 只在签发时返回一次
- 服务端只存哈希，不存原始值

哈希建议：

- `SHA-256`

## 数据模型设计

建议新增一张数据库表，而不是直接放 Redis。

原因：

- 设备列表查询是强需求
- 设备吊销是强需求
- 需要长期保留设备元数据
- 当前项目本身已经依赖 PostgreSQL

## 表名建议

```text
user_device_sessions
```

## 字段建议

### 核心字段

- `id`
- `user_id`
- `token_hash`
- `device_name`
- `device_type`
- `scope`
- `expires_at`
- `last_used_at`
- `created_at`
- `revoked_at`

### 可选辅助字段

- `client_version`
- `platform`
- `last_ip`
- `last_user_agent`

第一阶段建议把可选字段控制在最少，不要把表设计得过重。

## 字段含义建议

### `device_type`

建议枚举值：

- `desktop`
- `widget`
- `phone`
- `other`

### `scope`

第一阶段建议不要做复杂 RBAC 子系统，先使用简单范围值。

建议值：

- `full_client`
- `widget_basic`

含义：

- `full_client`：用于独立桌面端，允许访问完整个人系统能力
- `widget_basic`：用于桌面小工具，仅允许访问明确开放的轻量接口

后续如果 widget 能力扩展，再细分范围。

建议接口全部归到现有认证模块下。

## 接口一：设备登录

### 路径

```text
POST /auth/device/login
```

### 用途

- 独立桌面端登录
- 桌面小工具首次绑定

### 请求体建议

```json
{
  "username": "demo",
  "password": "demo_password",
  "device_name": "Elric Desktop",
  "device_type": "desktop",
  "scope": "full_client"
}
```

### 规则

- 使用用户名密码校验身份
- 校验账号启用状态
- 根据 `device_type` 与 `scope` 判断是否允许签发
- 创建 `user_device_session`
- 返回原始设备令牌与当前用户信息

### 响应体建议

```json
{
  "token": "pst_dev_xxx",
  "expires_at": "2026-06-02T12:00:00Z",
  "session": {
    "id": "018f....",
    "device_name": "Elric Desktop",
    "device_type": "desktop",
    "scope": "full_client",
    "created_at": "2026-05-03T12:00:00Z",
    "last_used_at": "2026-05-03T12:00:00Z"
  },
  "user": {
    "id": "018f....",
    "username": "demo",
    "nickname": "demo",
    "role": "user"
  }
}
```

## 接口二：当前设备登出

### 路径

```text
POST /auth/device/logout
```

### 请求头

```text
Authorization: Bearer pst_dev_xxx
```

### 用途

- 当前原生客户端主动退出

### 行为

- 查找当前设备会话
- 设置 `revoked_at`
- 返回 `204 No Content`

## 接口三：获取当前账号设备列表

### 路径

```text
GET /auth/device/sessions
```

### 用途

- 在 Web 控制台或桌面端展示“已登录设备”

### 返回内容建议

- `id`
- `device_name`
- `device_type`
- `scope`
- `created_at`
- `last_used_at`
- `expires_at`
- `revoked_at`
- `is_current`

## 接口四：吊销指定设备

### 路径

```text
DELETE /auth/device/sessions/{session_id}
```

### 用途

- 下线指定桌面端
- 下线指定小工具

### 权限

- 必须是当前用户自己的设备
- 或者超级管理员用于运维处理

## 接口五：续期当前设备会话

### 路径

```text
POST /auth/device/renew
```

### 是否第一阶段必须

- 可选

### 建议

如果第一阶段为了简化实现，可以先不做单独续期接口，而是在每次鉴权成功时按规则更新 `last_used_at`，并在接近过期时滑动延长 `expires_at`。

如果后续需要更明确的会话控制，再补这个接口。

## 绑定式小工具登录建议

桌面小工具不建议默认直接保存账号密码。

建议两种接入模式：

### 模式一：账号密码直接登录

优点：

- 实现快

缺点：

- 小工具需要处理完整登录 UI
- 用户体验一般

### 模式二：主程序签发小工具凭证

优点：

- 小工具不直接接触账号密码
- 可以默认使用 `widget_basic` 范围
- 更符合“小工具从属于主程序”的关系

缺点：

- 需要主程序先登录

当前更推荐模式二作为长期方向，但第一阶段可以先做模式一，快速打通链路。

## 鉴权依赖设计

当前浏览器登录使用 Cookie 读取 Session。

原生客户端需要新增一套依赖：

- 从 `Authorization` 头读取 Bearer Token
- 对 token 做哈希
- 查询 `user_device_sessions`
- 校验：
  - 未吊销
  - 未过期
  - 用户仍然有效

建议新增文件：

- `apps/cloud/backend/app/shared/auth/device_deps.py`

建议提供：

- `get_current_user_from_device_token`
- `get_current_device_session`
- `require_scope`

## 范围控制建议

当前第一阶段建议只做轻量范围校验，不上复杂权限系统。

### `full_client`

允许：

- 当前账号的全部个人系统能力

### `widget_basic`

允许：

- 读今日待办
- 新增简单待办
- 读摘要统计
- 读提醒信息

不允许：

- 用户资料修改
- 密码修改
- 文件管理
- 后台管理
- 高风险写操作

## 设备过期策略建议

建议先给出固定时长，再根据实际使用调整。

### 独立桌面端

- 默认有效期：`30 天`

### 桌面小工具

- 默认有效期：`90 天`

原因：

- 小工具更偏常驻能力
- 但仍然要保留吊销能力

如果后续觉得 widget 风险更高，也可以反过来缩短到 `30 天`。

## 服务端校验流程建议

每次原生客户端请求时：

1. 读取 `Authorization` 头
2. 提取 Bearer Token
3. 计算 `token_hash`
4. 查询 `user_device_sessions`
5. 判断 `revoked_at` 是否为空
6. 判断 `expires_at` 是否过期
7. 判断关联用户是否存在且启用
8. 更新 `last_used_at`
9. 放行请求

## 错误码建议

### 认证失败

- `401 Unauthorized`

适用情况：

- Token 缺失
- Token 无效
- Token 已过期
- Token 已吊销

### 权限不足

- `403 Forbidden`

适用情况：

- `widget_basic` 访问超范围接口
- 被禁用账号访问

## 与现有 Web 认证的边界

需要明确下面几点：

- Web 端继续使用现有 `/auth/login`
- 原生端使用新 `/auth/device/login`
- 两套认证入口并存
- 但用户、权限、账号状态、设备管理属于统一体系

这能避免后续把现有 Web 逻辑改乱。

## 前端共享层改造建议

当前 `packages/domain/src/auth/store.ts` 更偏浏览器会话恢复。

后续建议改成两层：

### 第一层：统一业务入口

- 登录
- 登出
- 恢复用户
- 获取当前用户

### 第二层：底层认证驱动

- `browser-session-driver`
- `device-token-driver`

这样可以做到：

- 页面层基本不关心底层载体
- 只有应用壳决定使用哪种驱动

## 第一阶段建议先不做的事

- 不做双令牌刷新体系
- 不做 OAuth
- 不做设备指纹风控
- 不做复杂 scope 组合
- 不做跨账号共享 widget 授权

这些都不是当前阶段的关键路径。

## 最终推荐

如果只保留最可执行的结论，建议如下：

- Web 保持当前 `Cookie Session + CSRF`
- 桌面端和小工具新增“设备会话令牌”
- 设备令牌采用不透明随机字符串，不采用 JWT
- 设备会话落 PostgreSQL
- 第一阶段采用单令牌方案
- 小工具使用 `widget_basic` 范围
