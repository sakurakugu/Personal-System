# 桌面端开发任务清单

## 目标

这份清单用于把桌面端与桌面小工具方案拆成可执行任务。

当前默认目标：

- 不破坏现有 Web 和手机端登录
- 先补后端设备认证能力
- 再建设独立桌面端
- 最后接入 Qt 小工具

## 总体顺序

- [ ] 第一阶段：冻结现有 Web 认证边界
- [ ] 第二阶段：补设备会话后端能力
- [ ] 第三阶段：扩展共享前端认证层
- [ ] 第四阶段：建设独立桌面端
- [ ] 第五阶段：建设 Qt 小工具
- [ ] 第六阶段：补设备管理页面与验证

## 第一阶段：冻结现有 Web 认证边界

目标：

- 明确浏览器继续走 `Cookie Session + CSRF`
- 不在这一阶段改动现有网页登录接口语义

任务：

- [ ] 确认 `packages/api/src/client.ts` 的浏览器认证逻辑保持不变
- [ ] 确认 `packages/domain/src/auth/store.ts` 的现有 Web 行为保持不变
- [ ] 确认 `apps/cloud/backend/app/modules/auth/api.py` 不被原生端逻辑直接污染

结果标准：

- 原有 Web 登录、登出、恢复会话行为不变

## 第二阶段：补设备会话后端能力

目标：

- 给原生桌面端与桌面小工具新增独立认证入口

### 数据库层

- [ ] 新增 `user_device_sessions` 表模型
- [ ] 新增 `DeviceSessionType` 枚举
- [ ] 新增迁移文件
- [ ] 为 `token_hash` 建唯一索引
- [ ] 为 `user_id`、`expires_at` 建索引

建议文件：

- `apps/cloud/backend/app/modules/auth/device_models.py`
- `apps/cloud/backend/alembic/versions/20260503_00_add_user_device_sessions.py`

### Schema 层

- [ ] 新增设备登录请求 Schema
- [ ] 新增设备登录响应 Schema
- [ ] 新增设备列表响应 Schema

建议文件：

- `apps/cloud/backend/app/modules/auth/device_schemas.py`

### Service 层

- [ ] 实现签发设备令牌
- [ ] 实现哈希存储
- [ ] 实现设备会话查询
- [ ] 实现设备会话吊销
- [ ] 实现设备范围校验

建议文件：

- `apps/cloud/backend/app/modules/auth/device_service.py`

### API 层

- [ ] 新增 `POST /auth/device/login`
- [ ] 新增 `POST /auth/device/logout`
- [ ] 新增 `GET /auth/device/sessions`

- `apps/cloud/backend/app/modules/auth/device_api.py`

### 共享鉴权依赖

- [ ] 从 `Authorization` 头解析 Bearer Token
- [ ] 解析并校验设备会话
- [ ] 提供当前用户依赖
- [ ] 提供 scope 校验依赖

建议文件：

- `apps/cloud/backend/app/shared/auth/device_deps.py`

结果标准：

- 后端已经可以独立支撑非浏览器客户端登录

## 第三阶段：扩展共享前端认证层

目标：

- 不让页面层直接感知 Cookie 与 Token 的差异

### `packages/domain`

- [ ] 为认证 store 抽象驱动接口
- [ ] 保持现有页面调用方式尽量不变
- [ ] 支持浏览器会话驱动
- [ ] 支持设备令牌驱动

建议落位：

- `packages/domain/src/auth/store.ts`
- `packages/domain/src/auth/context.ts`
- `packages/domain/src/auth/runtime.ts`
- 新增 `packages/domain/src/auth/drivers/*`

### `packages/api`

- [ ] 保留当前 `withCredentials` 模式
- [ ] 增加可选 `Authorization` 注入能力
- [ ] 保证浏览器模式和原生模式互不干扰

建议落位：

- `packages/api/src/client.ts`
- 可选新增 `packages/api/src/auth.ts`

结果标准：

- 应用壳可以选择认证驱动
- 业务页面不需要到处写平台分支

## 第四阶段：建设独立桌面端

默认推荐路线：

- `Tauri + 现有 Vue 前端`

目标：

- 以最小成本得到独立电脑端

### 目录规划

- [ ] 新建 `apps/desktop/`
- [ ] 明确它复用哪些来自 `apps/cloud/frontend` 的页面或壳
- [ ] 明确它自己的桌面专属入口与配置

### 接入任务

- [ ] 选择桌面端认证驱动为 `device-token-driver`
- [ ] 首次登录接 `/auth/device/login`
- [ ] 本地安全保存设备令牌
- [ ] 启动时恢复用户
- [ ] 登出时调用 `/auth/device/logout`

### 平台能力

- [ ] 规划托盘
- [ ] 规划系统通知
- [ ] 规划开机启动
- [ ] 规划窗口管理

结果标准：

- 用户可以用独立电脑端登录并稳定恢复登录态

## 第五阶段：建设 Qt 小工具

目标：

- 提供高频、轻量、低风险的桌面常驻入口

### 范围控制

- [ ] 确定首期只做待办、摘要、提醒
- [ ] 不做后台管理
- [ ] 不做高风险资料编辑

### 认证接入

- [ ] 小工具接入 `widget_basic` 范围设备令牌
- [ ] 优先评估“主程序签发小工具凭证”
- [ ] 如果首期为快速落地，可先使用独立登录

### API 收敛

- [ ] 梳理小工具只需要的接口
- [ ] 为高频接口评估是否要单独做聚合接口

结果标准：

- 小工具不依赖浏览器 Cookie
- 小工具只持有轻权限凭证

## 第六阶段：设备管理页面与验证

目标：

- 让用户可见、可控、可吊销设备

### 页面能力

- [ ] 在 Web 控制台增加“登录设备管理”
- [ ] 展示设备名称、类型、范围、最近活跃时间
- [ ] 支持踢掉指定设备
- [ ] 支持踢掉全部原生设备

建议优先落在：

- `apps/cloud/frontend/src/modules/auth/dashboard/`

### 验证

- [ ] 验证浏览器登录不受影响
- [ ] 验证桌面端可恢复登录态
- [ ] 验证吊销后原生端请求立即失效
- [ ] 验证 widget 无法访问超范围接口

结果标准：

- 设备认证不仅能用，而且可管理

## 验收标准

- [ ] Web 登录、登出、会话恢复行为完全不变
- [ ] 后端支持设备登录
- [ ] 可列出设备
- [ ] 可吊销设备

### 第二批验收

- [ ] 独立桌面端可稳定登录
- [ ] 独立桌面端可恢复登录态

## 检查与验证建议

根据当前仓库约定，修改完成后建议至少执行：

### Python

- [ ] `ruff check`
- [ ] `mypy`

### Node

- [ ] `npm run lint`
- [ ] `npm run typecheck`

如果涉及数据库结构变更：

- [ ] 增加 Alembic 迁移
- [ ] 本地执行迁移验证

## 当前推荐的实际落地顺序

如果只考虑性价比，推荐严格按下面顺序推进：

1. 后端设备会话模型与接口
2. 共享认证驱动抽象
3. Web 端设备管理页面
4. 独立桌面端
5. Qt 小工具

这个顺序的好处是：

- 先把认证底座补齐
- 再做客户端，不会反复返工
- 小工具可以晚于主程序，风险更低
