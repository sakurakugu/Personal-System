# 文娱推荐模块规划

## 为什么要做

当前云端博客里的“追番”页面，本质上只是一个基于 `Bangumi` 公开收藏接口的前端展示页：

- 数据不在本地数据库
- 没有后台录入和维护能力
- 内容范围偏 `Bangumi`，不适合覆盖书籍、电影、剧集等更广的文娱内容
- 页面命名和业务语义已经不再贴合当前需求

现在要做的不是简单改文案，而是把这部分升级成一个真正可维护、可扩展、可落库的“文娱推荐”模块。

一句话定义：

`文娱推荐模块是个人文娱内容的管理与展示层，用来记录、筛选、推荐和沉淀游戏、小说、书籍、动画、漫画、电影等作品。`

## 当前状态

截至 `2026-05-26`，当前仓库中的相关实现仍是旧的 `Bangumi` 展示方案：

- 前台路由：`/bangumi`
- 博客视图键：`bangumi`
- 页面标题：`追番记录`
- 横幅标题：`番组计划`
- 导航入口：`追番`
- 后端仅有 `Bangumi` 代理接口

当前没有：

- 独立数据库表
- 独立业务模块
- 控制台管理页
- 本地录入、编辑、删除能力

因此本规划的目标是：

- 去掉 `Bangumi` 依赖
- 改为数据库存储
- 增加控制台维护能力
- 增加博客前台展示能力

## 模块定位

文娱推荐模块的职责是：

- 管理个人接触过或计划接触的文娱作品
- 记录作品的主分类、状态、评分、标签、简介、描述等信息
- 作为博客前台“已阅 / 文娱推荐”页面的数据来源
- 作为后续扩展导入、筛选、推荐展示的基础

文娱推荐模块不负责：

- 临时资料收纳
- 网页素材中转
- 附件原始存储
- 公开文章写作

边界说明：

- `collections`：偏素材收纳和待整理输入层
- `media`：偏文娱作品记录和推荐展示
- `articles`：偏正式内容输出
- `files`：偏文件本体存储

## 分类设计

### 主分类

主分类采用固定集合，由代码维护，不做用户动态配置。

当前确认的主分类为：

- `game`：游戏
- `novel`：小说
- `book`：书籍
- `anime`：动画
- `comic`：漫画
- `movie`：电影
- `tv`：剧集
- `music`：音乐
- `other`：其他

说明：

- 小说不并入书籍，单独作为主分类
- 主分类只允许单选
- 主分类建议使用字符串字段存库，由后端做校验，不直接使用 PostgreSQL 原生枚举

这样做的原因是：

- 代码层更直观
- 后续调整主分类时不必承受数据库枚举迁移成本
- 足够稳定，但保留未来修改空间

### 子分类

子分类采用可增减模式，不作为固定主分类的一部分。

建议字段名：

- `genres`

子分类示例：

- 玄幻
- 修仙
- 校园
- 悬疑
- 科幻
- 恋爱

### 标签

标签用于承载跨维度属性，不纳入主分类。

建议字段名：

- `tags`

标签示例：

- 多女主
- 剧场版
- 动画电影
- Galgame
- 治愈
- 黑深残

规则说明：

- 主分类表达“这个作品主要是什么”
- 子分类表达“这个作品属于什么题材 / 风格”
- 标签表达“这个作品还有哪些补充属性”

例如“动画电影”的处理方式：

- 主分类：`movie` 或 `anime`，按预先统一规则二选一
- 标签：`动画电影`

统一约定：

- 影院 / 长篇放映作品，优先归 `movie`
- 连载番 / OVA / TV 系列，优先归 `anime`
- 交叉属性一律用标签补充

## 状态设计

状态采用枚举值，不单独以布尔值表达是否已看过 / 玩过。

当前确认的状态：

- `planned`：想看 / 想玩 / 想读
- `doing`：在看 / 在玩 / 在读
- `done`：已看 / 已玩 / 已读
- `paused`：搁置
- `dropped`：弃坑

说明：

- 前台如果需要“是否已体验”语义，可由 `status === 'done'` 推导出计算字段
- 不单独存 `is_consumed`，避免状态和布尔值冲突

## 评分设计

评分采用 `1-10` 区间。

建议规则：

- `rating` 可空
- 填写时只允许 `1` 到 `10`
- 第一版按整数处理，不做小数评分

这样更简单，也足够满足当前自用场景。

## 字段设计

第一版建议主表 `media_items` 包含以下字段：

- `id`
- `user_id`
- `title`
- `original_title`
- `media_type`
- `status`
- `rating`
- `creator`
- `summary`
- `description`
- `genres`
- `tags`
- `cover_file_id`
- `created_at`
- `updated_at`

字段说明：

- `title`：作品名称，必填
- `original_title`：原名，可空
- `media_type`：主分类，必填
- `status`：体验状态，必填
- `rating`：评分，`1-10`，可空
- `creator`：作者 / 导演 / 工作室 / 开发商，可空
- `summary`：客观简介，可空
- `description`：主观描述 / 推荐语，可空
- `genres`：子分类数组，可空
- `tags`：标签数组，可空
- `cover_file_id`：封面文件，可空

### 关于 `summary` 和 `description`

两者都保留。

- `summary` 用于放作品本身的简介
- `description` 用于放自己的评价或推荐语

原因：

- 前台卡片区和详情区可以分开使用
- 后续做摘要展示更灵活
- 不会把“作品信息”和“个人观点”混在一个字段里

### 关于 `genres` 和 `tags`

第一版建议直接使用 PostgreSQL 数组字段：

- `genres text[]`
- `tags text[]`

原因：

- 开发成本低
- 足够满足第一版筛选
- 不必一开始就上独立字典表和关联表

后续如果明确需要：

- 全局子分类管理
- 标签统计中心
- 统一别名治理

再拆成独立表即可。

## 数据库设计建议

第一版建议：

- 新建主表 `media_items`
- 可选给 `media_type`、`status`、`created_at` 建组合索引
- `cover_file_id` 关联现有 `files` 表

建议索引：

- `ix_media_items_user_id_media_type_status_created_at`
- `ix_media_items_user_id_status_created_at`
- `ix_media_items_user_id_rating_created_at`

如果后续有公开展示和排序需求，再视情况增加：

- `published_at`
- `sort_order`
- `is_visible`
- `is_recommended`

当前第一版可以先不加，避免过早设计。

## 风险与注意点

### 不要直接复用 `collections`

虽然 `collections` 已经有：

- 标题
- 备注
- 标签
- 附件
- 列表页

但它的定位是“待整理素材收纳”，和“文娱作品记录”不是一个领域。

如果强行复用，会出现：

- `type` 语义不对
- `status` 语义不对
- 表单字段不贴合
- 前台展示语义混乱

因此本次建议新建独立模块，不在 `collections` 上继续叠语义。

### 主分类固定，字段值仍建议走字符串校验

这是为了兼顾：

- 业务稳定
- 代码清晰
- 后续调整成本

不要一开始把数据库层绑死成原生枚举。

### `done` 状态可以推导“是否已阅”

不要同时维护：

- `status`
- `is_consumed`

否则后续极易出现数据冲突。

## 最终结论

本次“追番 -> 文娱推荐”的改造，最终确定方向为：

- 路由统一改为 `/media`
- 旧 `Bangumi` 方案彻底移除
- 新增独立 `media` 模块
- 数据表使用 `media_items`
- 主分类固定、子分类和标签可扩展
- 状态使用枚举值
- 评分使用 `1-10`
- `summary`、`description` 都保留且允许为空

后续具体开发时，按本文件作为实施基线执行。
