# 手机端亮屏解锁记录方案

## 目标

在手机端后台轻量收集以下状态，并在打开 App 时查看统计结果：

- 是否亮屏
- 是否解锁
- 是否正在使用手机
- 每天解锁次数
- 每天解锁时间点
- 每天亮屏总时长
- 每天解锁后使用总时长

约束如下：

- 尽量轻量，不做高频常驻轮询
- 尽量不增加额外系统常驻通知
- 优先复用当前 `apps/phone`，不新开独立小工具或独立服务

---

## 结论

推荐方案：

- 基于当前手机端实现
- Android 原生侧通过 `UsageStatsManager.queryEvents()` 读取系统已经记录的使用事件
- 在当前 App 启动、回前台或低频后台任务时补采事件
- 将事件汇总为本地统计数据，打开 App 时直接展示

不推荐方案：

- 不建议新开独立 App 或独立仓库
- 不建议做前台常驻服务
- 不建议依赖 `ACTION_SCREEN_ON` 一类广播做主链路
- 不建议上无障碍服务

---

## 为什么选这个方案

### 1. 足够轻量

`UsageStatsManager` 读取的是 Android 系统已经记录好的事件，不需要应用自己常驻监听，也不需要高频保活。

这比以下方案都更轻：

- 常驻后台服务
- 前台服务
- 高频定时轮询
- 广播常驻接收

### 2. 更符合 Android 近年的限制

Android 8 以后，后台广播、后台启动服务、隐式广播接收都越来越受限制。  
如果主链路依赖 `ACTION_SCREEN_ON`、`ACTION_USER_PRESENT` 这类广播，稳定性和兼容性都不如直接读取系统使用事件。

### 3. 能覆盖你的核心需求

通过 `UsageEvents.Event` 可以读到以下关键事件：

- `SCREEN_INTERACTIVE`：屏幕进入可交互状态，可近似视为亮屏
- `SCREEN_NON_INTERACTIVE`：屏幕进入不可交互状态，可近似视为灭屏
- `KEYGUARD_HIDDEN`：锁屏被隐藏，可近似视为解锁
- `KEYGUARD_SHOWN`：锁屏显示，可近似视为重新锁定

这已经足够计算：

- 亮屏次数
- 解锁次数
- 亮屏时长
- 解锁后使用时长

---

## 对“是否使用手机”的定义

建议在产品层定义为：

`亮屏 && 已解锁`

原因：

- “是否亮屏”只能说明屏幕被点亮
- “是否解锁”才能说明用户真正进入可操作状态
- 两者组合更接近“正在使用手机”

如果后面要更严格判断“是否正在主动使用”，可以再叠加前台应用事件，但第一版没必要复杂化。

---

## 架构建议

### 目录归属

建议按现有仓库分层放置：

- `apps/phone/android/...`
  - Android 原生插件实现
- `packages/platform`
  - 暴露跨端平台能力接口
- `packages/domain`
  - 统计模型、汇总逻辑、本地状态管理
- `apps/phone/src/modules/...`
  - 页面入口与展示

### 是否新开服务

结论：

- 不新开独立小工具
- 不新开独立 Android 进程
- 不新开云端服务
- 只在当前手机端内增加一个原生能力模块

原因：

- 采集依赖本机系统事件，天然属于手机端能力
- 云端无法直接感知设备亮屏或解锁
- 单独拆一个小工具会增加维护成本、权限管理成本和数据同步复杂度

## 实现方案

### 一、Android 原生插件

建议新增一个 Capacitor 自定义插件，对外提供最小接口：

- `检查使用情况权限()`
- `打开使用情况权限设置()`
- `读取屏幕使用事件(开始时间, 结束时间)`

返回事件建议统一为：

```ts
type 屏幕使用事件类型 =
  | 'screen_interactive'
  | 'screen_non_interactive'
  | 'keyguard_hidden'
  | 'keyguard_shown'

interface 屏幕使用事件 {
  类型: 屏幕使用事件类型
  时间戳: number
}
```

Android 内部映射关系：

- `SCREEN_INTERACTIVE` -> `screen_interactive`
- `SCREEN_NON_INTERACTIVE` -> `screen_non_interactive`
- `KEYGUARD_HIDDEN` -> `keyguard_hidden`
- `KEYGUARD_SHOWN` -> `keyguard_shown`

### 二、权限处理

这个能力依赖的是 **Usage Access**，不是普通运行时弹窗权限。

实现上需要：

- 检查当前是否已授权使用情况访问
- 如果未授权，跳转到系统设置页

系统设置入口：

- `Settings.ACTION_USAGE_ACCESS_SETTINGS`

注意：

- `PACKAGE_USAGE_STATS` 不是普通弹窗权限
- 用户需要手动在系统设置里为你的 App 开启

### 三、事件补采

不要做实时常驻监听，改为“按时间游标补采”。

建议维护一个本地游标：

- `lastCollectedAt`

每次补采时：

1. 读取 `[lastCollectedAt, now]` 区间内的系统事件
2. 做排序和去重
3. 写入统计汇总
4. 更新 `lastCollectedAt`

建议的补采时机：

- App 冷启动时
- App 从后台回前台时
- 用户进入统计页面时
- 用户手动刷新时

### 四、低频后台补采

如果担心长时间不打开 App 导致系统事件过期，可以增加一个低频后台补采任务。

建议：

- 使用 `WorkManager`
- 每 6 小时或 12 小时补采一次

不建议：

- 15 分钟高频执行
- 常驻服务
- 前台保活

说明：

- `WorkManager` 周期任务最小间隔是 15 分钟
- 实际执行并不精确，会受系统省电策略影响
- 对当前需求来说，低频补采已经足够

## 统计规则

### 一、亮屏次数

每遇到一次 `screen_interactive`，亮屏次数加一。

### 二、解锁次数

每遇到一次 `keyguard_hidden`，解锁次数加一。

### 三、亮屏总时长

按以下状态对计算：

- `screen_interactive` 作为亮屏开始
- `screen_non_interactive` 作为亮屏结束

区间时长累加为当天亮屏总时长。

### 四、解锁后使用总时长

建议规则：

- `keyguard_hidden` 作为使用开始
- `keyguard_shown` 或 `screen_non_interactive` 作为使用结束

这样能覆盖：

- 解锁后主动锁屏
- 解锁后直接灭屏

### 五、跨天拆分

如果一段亮屏或使用区间跨天，需要拆分到对应日期：

- 例如 `23:58 -> 00:10`
- 前一天记 2 分钟
- 后一天记 10 分钟

否则每天统计会不准。

## 数据模型建议

### 原始事件

原始事件不建议长期无限保存。  
建议只短期缓存，用于调试和重新汇总。

可选结构：

```ts
interface 原始屏幕事件记录 {
  时间戳: number
  类型: 'screen_interactive' | 'screen_non_interactive' | 'keyguard_hidden' | 'keyguard_shown'
}
```

### 每日汇总

建议重点保存每日汇总数据：

```ts
interface 每日手机使用汇总 {
  日期: string
  亮屏次数: number
  解锁次数: number
  亮屏总时长毫秒: number
  解锁使用总时长毫秒: number
  解锁时间点列表: number[]
}
```

### 本地元数据

```ts
interface 手机使用采集元数据 {
  最后采集时间戳: number
  最后汇总时间戳: number
  是否已授权使用情况访问: boolean
}
```

## 页面展示建议

第一版页面只做简单统计即可，不要一开始做复杂图表。

建议展示：

- 今天亮屏次数
- 今天解锁次数
- 今天亮屏总时长
- 今天解锁后使用总时长
- 最近 7 天趋势
- 今天的解锁时间点列表

如果后续要增强，再补：

- 日历热力图
- 分时段柱状图
- 工作日/休息日对比
- 解锁高峰时段分析

## 兼容性与边界

### 1. 数据不是实时推送

这是“补采模式”，不是“事件发生瞬间推送到前端”。  
但你的需求只是打开 App 查看统计，这个模式完全够用。

### 2. 系统事件不是永久保存

官方说明 `queryEvents()` 的系统事件只会保留最近几天。  
所以不能一直不打开 App，期望系统替你长期保存完整历史。

解决方式：

- 打开 App 时及时补采
- 可选增加低频 `WorkManager` 周期任务

### 3. 部分厂商系统可能更激进

某些国产系统会对后台任务更激进，导致低频任务执行时间不稳定。  
不过这不会影响你在前台打开 App 时补采数据，只会影响“长期不打开 App 时的自动兜底补采”。

### 4. “亮屏”与“实际使用”不是完全等价

屏幕亮了不代表一定在使用。  
因此统计上要区分：

- 亮屏时长
- 解锁后使用时长

后者更接近真实使用。

---

## 不推荐方案说明

### 1. 广播主链路

不建议将 `ACTION_SCREEN_ON`、`ACTION_USER_PRESENT` 作为主链路。

原因：

- Android 新版本限制更多
- 后台接收稳定性不如系统事件查询
- 兼容性成本更高

### 2. 前台服务

不建议为了这个需求上前台服务。

原因：

- 需要常驻通知
- 更耗电
- 维护成本高
- 和“轻量不占用”的目标相反

### 3. 无障碍服务

不建议。

原因：

- 权限过重
- 用户感知强
- 审核和系统信任风险更高
- 当前需求完全用不上

---

## 推荐落地顺序

### 第一阶段

先做最小可用版本：

- Android 插件读取 `UsageEvents`
- 前端检查权限并跳转授权
- 启动时补采事件
- 本地汇总每天的亮屏次数、解锁次数、时长
- 页面展示最近几天统计

### 第二阶段

再补稳定性：

- 增加 `lastCollectedAt`
- 增加事件去重
- 增加跨天拆分
- 增加异常日志

### 第三阶段

最后再做增强：

- `WorkManager` 低频补采
- 云端同步
- 趋势图表
- 更多使用分析

---

## 对当前仓库的具体建议

建议新增以下能力分层：

- `apps/phone/android/...`
  - 新增屏幕使用事件 Capacitor 插件
- `packages/platform/src/...`
  - 新增手机使用采集平台接口
- `packages/domain/src/...`
  - 新增手机使用统计 store 与汇总逻辑
- `apps/phone/src/modules/...`
  - 新增统计页面或挂到个人页/工具页

日志建议：

- 原生侧打印补采开始、结束、事件数量、权限状态
- 前端打印采集区间、汇总结果、失败原因

这样后续排查问题会简单很多。

---

## 最终决策

针对“后台轻量收集是否亮屏、是否解锁、是否使用手机，并在打开 App 时查看解锁时间和次数”的需求，最合适的方案是：

- 用当前 `apps/phone` 实现
- 不新开独立小工具
- 不做常驻前台服务
- 通过 `UsageStatsManager` 补采系统事件
- 在本地做每日汇总展示

这是当前实现复杂度、功耗、稳定性三者之间最平衡的方案。
