# 文件回收站与自动清理设计

## 背景

当前文件模块已经有完整的资源管理器、目录树、上传、移动、重命名、批量删除和打包下载能力，但删除仍然偏“物理删除”。普通文件一旦删除，数据库记录会被删除，提交成功后再尽力删除对象存储中的文件。这个行为对自用系统也有误删风险，尤其是批量删除和目录整理时。

本文档先记录基于当前代码的现状和后续设计，不代表功能已经实现。

## 当前代码现状

### 后端模型

- 普通文件表对应 `apps/cloud/backend/app/modules/files/models.py` 中的 `File`。
- 普通文件夹表对应同文件中的 `FileFolder`。
- `File` 当前字段包括 `id`、`user_id`、`folder_id`、`purpose`、`original_name`、`storage_key`、`size`、`mime_type`、`created_at`。
- `FileFolder` 当前字段包括 `id`、`user_id`、`parent_id`、`name`、`created_at`、`updated_at`。
- 普通文件和文件夹当前都没有 `is_deleted`、`deleted_at`、`purge_after` 等软删除字段。
- `FilePurpose` 后端当前包含 `file`、`article_image`、`moment_image`。前端类型还展示 `media_asset`，但文娱资源来自 `文娱资源` 表，不属于 `files` 表枚举。

### 后端删除行为

`apps/cloud/backend/app/modules/files/operations.py` 里的 `删除文件` 当前有三条路径：

- 普通文件：查询 `File.user_id == user.id` 且 `File.purpose == FilePurpose.file`，找到后 `db.delete(record)`，提交成功后调用 `尽力删除对象(storage_key)`。
- 文章图片：通过 `文章图片` 关联 `文章`，要求作者是当前用户且文章未删除，找到后删除图片记录，提交成功后删除对象。
- 动态图片：通过 `动态图片` 关联 `动态`，要求作者是当前用户且动态未删除，找到后删除图片记录，提交成功后删除对象。

`删除文件夹` 当前只允许删除空文件夹：

- 如果存在子文件夹，返回 `400 文件夹下仍有子文件夹，无法删除`。
- 如果存在普通文件，返回 `400 文件夹下仍有文件，无法删除`。
- 空文件夹会直接 `db.delete(folder)` 并提交。

### 资源管理器展示行为

`apps/cloud/backend/app/modules/files/explorer.py` 当前展示逻辑：

- 任意目录下展示普通文件夹和普通文件。
- 根目录额外展示文章图片、动态图片和文娱资源。
- 文章、动态、文娱条目本身已删除时，对应资源默认不进入普通资源管理器列表。
- 搜索同样会查询普通文件夹、普通文件、文章图片、动态图片和文娱资源。

### 文件访问行为

`apps/cloud/backend/app/api/public_files.py` 通过 `/files/{storage_key}` 读取对象内容：

- 文章图片和动态图片会检查父级文章/动态是否已删除；父级已删除时仅允许有管理权限的用户读取，否则返回 404。
- 文娱资源在公开封面等场景下支持公开缓存，否则要求签名或当前用户权限。
- 普通文件当前没有软删除状态，签名有效或当前用户匹配时即可读取。

如果后续给普通文件加回收站，必须同步修改这个读取入口。普通文件进入回收站后，即使旧签名 URL 仍在有效期内，也应该默认返回 404 或 410，避免“已删除文件还能通过旧链接访问”。

### 前端行为

`packages/modules/文件/src/api.ts` 当前只有这些删除接口：

- `DELETE /files/{id}`
- `DELETE /files/folders/{id}`

`packages/modules/文件/src/core/batch-actions.ts` 当前批量删除文案是“删除资源”，成功提示是“已删除 N 项资源”。没有回收站视图、恢复、彻底删除、自动清理时间展示。

## 推荐目标

推荐给普通文件模块添加回收站，并添加自动清理策略。第一版已确认保留 `30 天`。自用系统里 30 天更适合文件，因为对象存储会占实际容量，且文件误删通常会在较短时间内发现。

第一版范围建议只覆盖普通文件和普通文件夹：

- 覆盖 `FilePurpose.file` 的普通文件。
- 覆盖 `FileFolder` 的普通文件夹。
- 暂不把文章图片、动态图片、文娱资源纳入文件模块回收站。
- 文章、动态、文娱资源继续跟随各自业务模块的回收站和永久删除语义。

这样做的原因是当前统一资源管理器里展示的是多来源资源。普通文件属于文件模块自身；文章图片、动态图片、文娱资源属于内容模块的附件或资源，直接放进文件模块回收站会引入“恢复文件是否恢复内容关系”“删除图片是否修改文章正文”“文娱封面是否影响公开展示”等跨模块副作用。

## 数据库设计

### 普通文件

建议给 `files` 表添加：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `is_deleted` | `bool` | 是否进入回收站，默认 `false` |
| `deleted_at` | `datetime/null` | 进入回收站时间 |
| `deleted_by` | `uuid/null` | 删除操作者，关联 `users.id`，用户被删后可设空 |
| `purge_after` | `datetime/null` | 可被自动清理的最早时间 |
| `purged_at` | `datetime/null` | 已物理删除时间，通常只用于异步清理日志或保留审计时使用 |

约束建议：

- `is_deleted = false` 时，`deleted_at`、`purge_after`、`purged_at` 应为空。
- `is_deleted = true` 时，`deleted_at` 和 `purge_after` 应非空。
- 普通列表和搜索需要增加 `File.is_deleted.is_(False)`。
- 回收站列表需要增加 `File.is_deleted.is_(True)`。

索引建议：

- `ix_files_user_id_is_deleted_purpose_folder_id_created_at`
- `ix_files_is_deleted_purge_after`

### 普通文件夹

建议给 `file_folders` 表添加：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `is_deleted` | `bool` | 是否进入回收站，默认 `false` |
| `deleted_at` | `datetime/null` | 进入回收站时间 |
| `deleted_by` | `uuid/null` | 删除操作者 |
| `purge_after` | `datetime/null` | 可被自动清理的最早时间 |

文件夹需要额外处理层级关系：

- 删除文件夹时，允许非空文件夹移入回收站，并递归标记所有子文件夹和普通文件。
- 恢复文件夹时，需要恢复整棵子树，或第一版只允许恢复整棵子树，不支持只恢复子节点。
- 如果父文件夹仍在回收站，恢复子文件夹时一并恢复父链。
- 同目录同名冲突时，恢复前应检查当前目标目录是否已有同名文件夹。冲突时返回 409，让前端提示用户先重命名或选择恢复到其他目录。

## 接口设计

### 普通浏览和搜索

现有接口默认只返回未删除资源：

- `GET /files/explorer`
- `GET /files/search`

改造要求：

- 普通文件查询增加 `File.is_deleted.is_(False)`。
- 普通文件夹树、面包屑、子文件夹查询增加 `FileFolder.is_deleted.is_(False)`。
- 打包下载不允许选择已删除文件或已删除文件夹。
- 移动、重命名不允许操作已删除文件或已删除文件夹。

### 回收站列表

建议新增：

```text
GET /files/trash
```

返回当前用户已删除的普通文件和普通文件夹，按 `deleted_at desc` 排序。第一版可以不做树形展示，只展示被删除的顶层资源：

- 如果父文件夹也已删除，子文件和子文件夹不单独展示。
- 如果单个文件被删除而父文件夹未删除，文件单独展示。

响应建议包含：

- `id`
- `type`: `file | folder`
- `name`
- `original_parent_id`
- `path`
- `deleted_at`
- `purge_after`
- `remaining_days`
- 文件资源额外包含 `size`、`mime_type`。

### 移入回收站

现有删除接口建议保持路径不变，但语义从硬删除改为移入回收站：

```text
DELETE /files/{file_id}
DELETE /files/folders/{folder_id}
```

普通文件删除：

- 只标记普通文件 `is_deleted = true`。
- 设置 `deleted_at = now`。
- 设置 `deleted_by = current_user.id`。
- 设置 `purge_after = now + 30 days`。
- 不删除对象存储。

普通文件夹删除：

- 递归标记文件夹子树和子树下普通文件。
- 不删除对象存储。
- 不影响文章图片、动态图片、文娱资源。

注意：当前 `DELETE /files/{id}` 还会删除文章图片和动态图片。改造时需要拆分语义：

- 当 `id` 命中普通文件时，执行移入回收站。
- 当 `id` 命中文章图片或动态图片时，文件模块不再直接删除，返回明确错误或前端直接隐藏删除入口。
- 前端点击文章图片或动态图片的管理动作时，跳转到对应文章/动态编辑页面处理，行为与文娱资源跳转到编辑页面保持一致。
- 这样可以避免文件模块绕过内容模块的正文引用、封面、Feed、缓存等业务关系。

### 恢复

建议新增：

```text
POST /files/{file_id}/restore
POST /files/folders/{folder_id}/restore
```

普通文件恢复：

- 校验文件属于当前用户，且 `is_deleted = true`。
- 如果原父文件夹已删除，一并恢复父链。
- 清空 `is_deleted`、`deleted_at`、`deleted_by`、`purge_after`。

普通文件夹恢复：

- 校验文件夹属于当前用户，且 `is_deleted = true`。
- 恢复该文件夹子树和其中普通文件。
- 同名冲突返回 409。

### 彻底删除

建议新增：

```text
DELETE /files/{file_id}/purge
DELETE /files/folders/{folder_id}/purge
```

彻底删除只允许对已经在回收站里的资源执行：

- 普通文件：删除数据库记录，提交成功后调用 `尽力删除对象(storage_key)`。
- 普通文件夹：递归收集子树普通文件的 `storage_key`，删除数据库记录，提交成功后批量 `尽力删除多个对象(storage_keys)`。
- 如果对象删除失败，保留 warning 日志。当前 `尽力删除多个对象` 已经有失败日志，但建议在文件模块再记录资源 ID、用户 ID 和数量，方便定位业务入口。

## 自动清理

建议新增文件模块清理服务：

```text
清理过期回收站文件(db, *, now=None, limit=500)
```

清理条件：

- `is_deleted = true`
- `purge_after <= now`

清理顺序：

1. 批量读取待清理普通文件和文件夹子树。
2. 收集所有 `storage_key`。
3. 删除数据库记录并提交。
4. 提交成功后调用 `尽力删除多个对象(storage_keys)`。
5. 记录清理日志：用户数、文件数、文件夹数、对象数、失败异常。

调度方式建议：

- 第一版可以接入应用启动后的轻量后台任务，每天运行一次。
- 如果不想在后端进程内做周期任务，可以先做管理命令或工具脚本，再由外部计划任务触发。
- 不建议依赖用户访问某个接口时顺手清理文件，因为文件对象较大，接口延迟和失败面会变复杂。

## 文件访问入口改造

`/files/{storage_key}` 必须识别普通文件回收站状态：

- 查询普通 `File` 时增加 `File.is_deleted.is_(False)`。
- 如果命中已删除普通文件，默认返回 404。
- 不建议对回收站文件继续允许签名 URL 访问。
- 回收站预览如果确实需要，可以新增专门的已删除文件预览接口，并强制当前用户权限，不复用公开签名 URL。

这样可以保证“移入回收站”从用户视角等同于不可访问，只是后台仍保留恢复能力。

## 前端改造点

建议在文件页面增加一个明确的回收站入口：

- 左侧目录树或工具栏增加“回收站”视图。
- 普通列表里的删除按钮文案改为“移入回收站”。
- 回收站视图提供“恢复”和“彻底删除”。
- 回收站里展示“将在 N 天后自动删除”。
- 批量删除确认文案从“确定删除选中的 N 项资源？”改为“确定将选中的 N 项资源移入回收站？”。
- 彻底删除确认必须明确“此操作不可恢复”。
- 文章图片、动态图片不展示删除按钮，展示“编辑文章”或“编辑动态”入口。
- 文娱资源继续保持现有只读逻辑，管理动作跳转到文娱编辑页面。

第一版前端不建议在回收站里支持移动、重命名、打包下载。

## 与其他模块的边界

### 文章图片和动态图片

当前文章和动态本身已有软删除、恢复和永久删除能力。文件资源管理器只是把图片展示出来，并通过统一接口支持重命名和删除。

推荐后续调整：

- 文件模块不直接删除文章图片和动态图片。
- 文件资源管理器中对文章图片展示“编辑文章”，对动态图片展示“编辑动态”，跳转到对应内容编辑页面。
- 内容图片的删除应回到文章/动态编辑流程里做，避免正文引用、封面、Feed、缓存等状态不一致。
- 如果未来确实要给内容图片也做回收站，应分别给 `文章图片`、`动态图片` 表补软删除字段，并在文章/动态读取、渲染、图片列表、永久删除时统一处理。

### 文娱资源

文娱资源当前在文件资源管理器中是只读展示，不通过文件模块删除。这个策略应保持。

文娱模块已有条目级软删除和恢复。资源级删除、封面替换、外部资源下载都属于文娱模块自己的副作用，不应混到普通文件回收站第一版里。

### 用户删除

当前用户删除逻辑会收集用户普通文件和文章图片的 `storage_key`，删除用户后清理对象存储。文件回收站不会改变账号删除的最终语义：删除用户仍应物理清理该用户对象存储。

如果后续给 `files` 表增加软删除字段，用户删除清理逻辑仍应查询该用户所有普通文件，包括已删除和未删除。

## 实施顺序

1. 增加 Alembic 迁移：给 `files`、`file_folders` 增加软删除字段、约束和索引。
2. 修改 `File`、`FileFolder` 模型和 Schema。
3. 修改资源管理器、搜索、移动、重命名、归档下载查询，默认排除已删除普通文件和文件夹。
4. 把普通文件和普通文件夹删除改为移入回收站。
5. 新增回收站列表、恢复、彻底删除接口。
6. 修改 `/files/{storage_key}`，禁止已删除普通文件通过旧签名访问。
7. 增加自动清理服务和调度入口。
8. 修改前端 API、类型、文件页面回收站视图、删除确认文案，以及文章图片/动态图片跳转编辑页入口。
9. 增加后端测试：软删除、恢复、彻底删除、自动清理、旧签名不可访问、文件夹递归删除恢复。
10. 增加前端类型检查和关键交互测试。
