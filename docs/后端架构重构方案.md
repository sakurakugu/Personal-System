# 后端架构重构方案

## 1. 背景

当前后端已经开始从“大单文件服务”向“领域子模块”演进，但目录边界仍然不统一：

- `app/api`、`app/models`、`app/schemas`、`app/services` 仍然按技术层横向分散。
- `articles`、`users`、`files`、`bills` 已经开始拆子目录，但 `todo`、`comment`、`collection`、`stats` 等仍是大文件。
- 旧聚合入口和新子模块并存，例如 `article_service.py`、`bill_service.py` 这类兼容导出文件仍在。
- 新增功能时往往需要同时修改路由、模型、Schema、服务多个顶层目录，落点不稳定。

本项目为自用项目，可以重构，不要求向前兼容。这里直接采用方案 2：`bootstrap + shared + modules`。

## 2. 重构目标

目标目录结构如下：

```text
backend/app/
  bootstrap/
    app.py
    lifespan.py
    middleware.py
    router.py

  shared/
    db/
      base.py
      session.py
    auth/
      deps.py
      cookie.py
      session.py
      password.py
    storage/
      client.py
      file_url.py
    kernel/
      config.py
      logger.py
      validation.py
      pagination.py

  modules/
    users/
      api.py
      models.py
      schemas.py
      service.py
      permissions.py
    articles/
      api.py
      models.py
      schemas.py
      service.py
      permissions.py
      search.py
    files/
      api.py
      models.py
      schemas.py
      service.py
      explorer.py
      folders.py
    comments/
      api.py
      models.py
      schemas.py
      service.py
    todos/
      api.py
      models.py
      schemas.py
      service.py
    collections/
      api.py
      models.py
      schemas.py
      service.py
    bills/
      api.py
      models.py
      schemas.py
      service.py
    system/
      api.py
      schemas.py
      service.py
    feed/
      api.py
      schemas.py
      service.py

  integrations/
    rss/
    holiday/
    bangumi/

  main.py
```

核心约束：

- `bootstrap` 只负责应用启动、生命周期、中间件、路由装配。
- `shared` 只放跨业务复用的基础设施，不放具体业务规则。
- `modules` 按领域聚合自己的 API、模型、Schema、服务实现。
- `integrations` 放外部集成能力，不和核心业务模块混放。
- 旧兼容导出层只允许短期存在，迁移完成后要删除。

## 3. 当前问题定位

- [ ] `app/api/v1` 下多个路由文件已经偏大，继续加接口会持续膨胀。
- [ ] `app/services/todo_service.py`、`app/services/collection_service.py`、`app/services/comment_service.py` 等单文件职责过多。
- [ ] `app/models`、`app/schemas` 顶层聚合方式导致新增一个业务时需要跨多个目录来回切换。
- [ ] `app/services/article_service.py`、`app/services/bill_service.py` 等聚合导出层会模糊真实实现入口。
- [ ] `app/api/deps.py` 这类通用依赖和业务依赖还没有彻底分层。
- [ ] `app/models/__init__.py`、`app/models/models.py`、`app/schemas/__init__.py`、`app/schemas/schemas.py` 这类全量导出文件长期容易变成新的耦合中心。
- [ ] 测试目前仍有部分路径依赖旧服务入口，后续迁移需要同步调整。

## 4. 目录职责约束

### 4.1 `bootstrap`

- [x] 将应用启动逻辑从 `app/main.py` 中拆到 `bootstrap`。
- [x] 将中间件、异常处理、生命周期管理拆成独立文件。
- [x] 将总路由注册逻辑集中到 `bootstrap/router.py`。
- [x] 保持 `main.py` 足够薄，只保留应用实例暴露。

### 4.2 `shared`

- [x] 将数据库引擎、会话、基类统一收敛到 `shared/db`。
- [x] 将认证 Cookie、Session、密码哈希、通用依赖收敛到 `shared/auth`。
- [x] 将对象存储访问、文件签名 URL 收敛到 `shared/storage`。
- [x] 将配置、日志、校验、分页等基础能力放到 `shared/kernel`。
- [ ] 进入 `shared` 的代码必须满足“跨两个以上模块可复用，且不依赖具体业务模块”。

### 4.3 `modules`

- [ ] 每个业务模块自己持有 `api.py`、`models.py`、`schemas.py`、`service.py`。
- [ ] 复杂模块允许继续拆成 `queries.py`、`commands.py`、`permissions.py`、`presentation.py` 等内部文件。
- [ ] 模块对外只暴露明确入口，禁止跨模块直接穿透内部私有实现。
- [ ] 模块间能通过共享基础设施解决的，不要互相复制实现。

### 4.4 `integrations`

- [ ] 将 RSS、节假日、Bangumi 这类外部能力单独归位。
- [ ] 避免把外部集成逻辑继续混在核心业务服务目录中。

## 5. 分阶段迁移清单

### 5.1 阶段一：建立新骨架

- [x] 新建 `app/bootstrap`、`app/shared`、`app/modules`、`app/integrations` 目录。
- [x] 搬迁 `config`、`logger`、`database`、`validation` 等基础设施到 `shared`。
- [ ] 保持旧 import 暂时可用，但新增代码优先走新目录。
- [ ] 明确新目录命名规范，避免出现 `module`、`modules`、`services` 混用。

### 5.2 阶段二：抽离启动层

- [x] 将 `main.py` 中的 `lifespan` 抽到 `bootstrap/lifespan.py`。
- [x] 将限流、CSRF、请求监控中间件拆到 `bootstrap/middleware.py`。
- [x] 将 API 路由装配逻辑集中到 `bootstrap/router.py`。
- [x] 让 `main.py` 只负责 `create_app()` 或导出 `app`。

### 5.3 阶段三：迁移基础设施

- [x] `app/core/database.py` 迁移到 `shared/db/session.py`。
- [x] `app/core/config.py` 迁移到 `shared/kernel/config.py`。
- [x] `app/core/logger.py` 迁移到 `shared/kernel/logger.py`。
- [x] `app/core/security.py` 迁移到 `shared/auth/password.py`。
- [x] `app/services/session_service.py`、`auth_cookie_service.py` 的通用部分迁移到 `shared/auth`。
- [x] `app/services/storage_service.py`、`file_url_service.py` 迁移到 `shared/storage`。
- [x] `app/api/deps.py` 拆成共享认证依赖与业务专属依赖。

### 5.4 阶段四：优先迁移重量级模块

建议迁移顺序：

- [x] `todos`
- [x] `collections`
- [x] `comments`
- [ ] `feed`
- [x] `system`

每个模块统一执行以下动作：

- [ ] 新建 `modules/<name>/` 目录。
- [ ] 将对应路由迁入模块内 `api.py`。
- [ ] 将对应 ORM 模型迁入模块内 `models.py`。
- [ ] 将对应 Pydantic 模型迁入模块内 `schemas.py`。
- [ ] 将原有服务逻辑迁入模块内 `service.py` 或其子文件。
- [ ] 调整 import 到模块内相对稳定的公开入口。
- [ ] 补齐或迁移对应测试文件引用路径。

### 5.5 阶段五：迁移已半拆分模块

- [x] 将 `articles` 从“`models/schemas/services/api` 分散”彻底收敛到 `modules/articles`。
- [x] 将 `users` 从“`services/users + user_service.py + api/v1/users.py` 混合”收敛到 `modules/users`。
- [x] 将 `files` 从“`services/files + api/v1/files.py + schemas/file.py` 混合”收敛到 `modules/files`。
- [ ] 将 `bills` 从“`services/bills + bill_service.py + api/v1/bills.py` 混合”收敛到 `modules/bills`。
- [ ] 将 `friend_links`、`moments`、`announcements` 等次级模块按同样规则归位。

### 5.6 阶段六：清理兼容层

- [ ] 删除 `app/services/article_service.py` 这类过渡聚合导出文件。
- [ ] 删除 `app/services/bill_service.py` 这类过渡聚合导出文件。
- [ ] 清理 `app/models/models.py`、`app/schemas/schemas.py` 等历史全量导出层。
- [ ] 清理不再使用的旧 import 路径。
- [ ] 确保目录边界收敛后，再统一整理 `__init__.py` 暴露策略。

### 5.7 阶段七：验证与收尾

- [ ] 运行 `ruff check backend/app backend/tests`
- [ ] 运行 `mypy backend/app backend/alembic`
- [ ] 逐个核心模块跑测试，优先覆盖被迁移模块。
- [ ] 确认 Alembic 环境仍可正常发现模型元数据。
- [ ] 更新 README 中的后端目录说明。
- [ ] 文档中记录新的模块新增流程，防止后续继续写回旧结构。

## 6. 模块迁移优先级

### 6.1 第一优先级

- [ ] `todos`：当前服务文件很大，后续还容易继续增长。
- [ ] `collections`：同时牵涉文章草稿、文件、待办等跨域调用，越晚拆越难。
- [ ] `comments`：权限、树结构、审核、点赞都混在一个服务文件里，适合尽早收口。

### 6.2 第二优先级

- [ ] `feed`
- [ ] `system`
- [ ] `stats`

### 6.3 第三优先级

- [ ] `articles`
- [ ] `users`
- [ ] `files`
- [ ] `bills`

这几个模块虽然已有一定拆分，但仍然没有完成目录闭环，适合在规则跑顺后统一收口。

## 7. 模块内部推荐结构

简单模块：

```text
modules/comments/
  api.py
  models.py
  schemas.py
  service.py
```

复杂模块：

```text
modules/articles/
  api.py
  models.py
  schemas.py
  queries.py
  commands.py
  permissions.py
  presentation.py
  search.py
```

约束清单：

- [ ] 优先按职责拆分，不按“一个文件一个接口”机械拆分。
- [ ] 查询密集逻辑进入 `queries.py`。
- [ ] 写操作密集逻辑进入 `commands.py` 或 `service.py`。
- [ ] 权限规则单独收敛到 `permissions.py`。
- [ ] 响应组装、格式转换单独收敛到 `presentation.py`。
- [ ] 只有模块足够复杂时再继续细拆，避免过度设计。

## 8. 跨模块依赖规则

- [ ] `modules` 可以依赖 `shared`，不能反向依赖。
- [ ] 模块之间优先依赖对方公开入口，不直接依赖内部私有文件。
- [ ] 外部集成优先通过 `integrations` 收口，不直接散落在业务模块各处。
- [ ] 涉及事务的一组操作，尽量在调用方模块内完成编排，避免多模块互相提交事务。
- [ ] 共享常量、通用分页、通用错误处理优先进入 `shared`，不要重复定义。

## 9. 本次重构落地顺序

- [ ] 先完成本方案文档并持续维护。
- [ ] 先搭建 `bootstrap/shared/modules/integrations` 新骨架。
- [ ] 先迁 `todo` 模块，作为第一批试点。
- [ ] 在 `todo` 迁移稳定后，按顺序迁移 `collections`、`comments`。
- [ ] 基础规则跑通后，再收口 `articles/users/files/bills` 这些已半拆分模块。
- [ ] 最后统一删除兼容层并清理旧目录残留。

## 10. 完成标准

- [ ] 新增业务功能时，能在单个模块目录内完成大部分开发。
- [ ] `main.py` 不再承载大量启动与中间件细节。
- [ ] `shared` 不再混入业务逻辑。
- [ ] 不再保留历史兼容导出层。
- [ ] 路由、模型、Schema、服务的落点规则明确且稳定。
- [ ] `ruff` 和 `mypy` 检查通过。
