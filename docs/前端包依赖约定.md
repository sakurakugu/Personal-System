# 前端包依赖约定

## 目标

这份约定用于约束当前前端 workspace 的依赖方向，避免后续继续出现：

- 应用层反向被公共层依赖
- 业务模块横向随意互相引用
- 平台差异重新散落回共享层
- 为了导入方便重新加回大量源码 alias

核心原则只有一句话：

- 依赖方向只能从上往下收敛，不能反向长回去

---

## 当前分层

```text
apps/*
packages/modules/*
packages/app-core
packages/domain
packages/api
packages/ui
packages/theme
packages/platform
```

可以按职责理解为：

- `apps/*`：平台壳层与应用装配
- `packages/modules/*`：前端业务模块包
- `packages/app-core`：公共装配与模块路由机制
- `packages/domain`：纯业务领域状态与流程
- `packages/api`：统一接口访问
- `packages/ui` / `packages/theme`：视觉基础层
- `packages/platform`：平台能力抽象与适配

---

## **推荐**依赖方向

### `apps/*` 可以依赖

- `@personal-system/module-*`
- `@personal-system/app-core`
- `@personal-system/domain`
- `@personal-system/api`
- `@personal-system/ui`
- `@personal-system/theme`
- `@personal-system/platform`

### `packages/modules/*` 可以依赖

- `@personal-system/app-core`
- `@personal-system/domain`
- `@personal-system/api`
- `@personal-system/ui`
- `@personal-system/theme`
- `@personal-system/platform`

### `packages/app-core` 可以依赖

- `@personal-system/domain`
- `@personal-system/api`
- `@personal-system/theme`
- `@personal-system/platform`

### `packages/domain` 可以依赖

- `@personal-system/api`

### `packages/ui` 可以依赖

- `@personal-system/theme`

### `packages/api` / `packages/theme`

- 默认不依赖上层业务包

---

## 明确禁止

### 禁止公共包依赖应用层

下面这种方向不允许出现：

- `packages/* -> apps/*`

原因：

- 会直接打破复用边界
- 会让桌面端、手机端、云端互相纠缠

### 禁止重新引入 `@personal-system/modules/*`

应用层和公共层统一使用：

- `@personal-system/module-auth`
- `@personal-system/module-todos`

不再新增这类旧风格导入：

- `@personal-system/modules/auth`
- `@personal-system/modules/todos`

### 禁止为了方便重新加回大批 `tsconfig paths`

当前前端已经改为 workspace 包解析。

只有这类别名可以继续保留：

- `@/*` 指向应用自己的 `src`

不再为公共包和第三方包维护大批源码直连 `paths` / Vite alias。

---

## 模块横向依赖规则

默认规则：

- `packages/modules/*` 之间不鼓励横向依赖

优先做法：

- 公共类型或流程下沉到 `domain`
- 公共组件下沉到 `ui`
- 公共接口能力下沉到 `api`

### 当前可接受的例外

现阶段这类依赖可以接受：

- `module-blog -> module-articles`
- `module-blog -> module-moments`

因为它们属于明确的业务聚合关系。

但如果横向依赖继续增多，就应回头抽公共层，而不是继续堆模块互相引用，除非是上述这种。

---

## 导出约定

每个 `packages/modules/*` 都应满足：

- 有自己的 `package.json`
- 有稳定包名 `@personal-system/module-*`
- 用 `exports` 显式声明公开入口

不建议：

- 应用直接引用包内未导出的深层私有文件
- 靠工作区相对路径跨包 import

---

## 新增模块时的建议

新增一个共享业务模块时，按这个顺序判断：

1. 这个能力是否真的会跨端复用
2. 如果会，是否应放入 `packages/modules/<name>`
3. 是否需要抽公共类型到 `domain`
4. 是否需要抽公共组件到 `ui`
5. 是否需要声明平台能力依赖到 `platform`

如果答案还不稳定，就先留在对应 `apps/*`，不要过早抽包。

---

## 检查方式

当前根目录可直接运行：

```bash
npm run check:frontend
```

或分别运行：

```bash
npm run lint:frontend
npm run typecheck:frontend
```

新增公共包或调整依赖方向后，至少要通过以上检查。
