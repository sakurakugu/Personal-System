# 桌面端图片工具增强方案

## 背景

当前图片工具入口位于 `packages/modules/工具/src/pages/图片工具页面.vue`，包含以下三个工作台：

- 图片编辑
- 格式转换
- 图片拼接

这三块能力目前主要依赖浏览器端的 `canvas` 完成导入、预览和导出，因此天然受到浏览器编解码能力限制。现状更适合：

- `PNG`
- `JPG`
- `WEBP`
- 部分环境下的 `AVIF`

对于以下格式，纯前端方案要么不稳定，要么会明显损失能力：

- `HEIC / HEIF`
- `TIFF`
- `PSD`
- `ICO`
- `BMP`
- 动态 `GIF`
- 需要保留 `EXIF / ICC / 拍摄信息` 的图片

目标是让桌面端支持更多格式，同时不要求云端同步支持。

## 目标

- 桌面端的图片编辑、格式转换、图片拼接支持更多格式
- 云端继续复用现有前端实现，不强行接入本地后端能力
- 尽量复用现有页面和交互，不复制一套桌面专属页面
- 将平台差异收敛到能力层，避免页面逻辑分叉
- 为后续继续扩展图片能力预留统一接口

## 非目标

- 本次不要求云端支持 `HEIC / TIFF / PSD / 动图 GIF` 等增强格式
- 本次不要求做成远程服务或上传到云端处理
- 本次不要求向前兼容当前浏览器端内部实现细节

## 现状判断

### 共享入口

桌面端和云端目前共用同一个图片工具页面入口：

- 桌面端路由引用 `@personal-system/module-tools` 中的 `ImageToolsPage`
- 云端前端也直接引用同一个 `ImageToolsPage`

这意味着如果直接复制一套桌面版图片工具页面，后续会出现两套 UI 和两套状态流，维护成本会很快失控。

### 桌面端本地能力基础已经存在

桌面端已经具备以下能力链路：

- `renderer` 通过 `preload` 暴露安全 API
- `preload` 通过 `ipcRenderer.invoke` 调主进程
- 主进程通过 `ipcMain.handle` 注册能力
- 主进程已可调用本地 Python 工具

仓库内已有图片分类工具作为成熟参考实现，因此图片工具增强应复用同一种模式。

## 推荐方案概览

推荐将图片工具改造成“共享 UI + 平台能力适配”的结构：

1. `packages/modules/工具` 继续保留页面、交互和参数表单
2. 抽离图片能力接口，不再让页面直接操作 `canvas.toBlob()` 作为唯一处理方式
3. 浏览器端继续使用现有前端本地实现
4. 桌面端增加 Electron IPC + 本地 Python 图片处理器
5. 页面根据当前运行时返回的能力，决定展示哪些格式和提示

一句话概括：

`同一套页面，按平台切换底层图片处理驱动`

## 架构设计

### 分层原则

推荐按下面的职责拆分：

- `packages/modules/工具`
  - 负责页面、工作台、参数收集、交互反馈
  - 不直接耦合 Electron 和 Python
- `packages/platform`
  - 定义图片工具运行时接口
  - 提供浏览器实现和桌面实现的统一访问入口
- `apps/desktop`
  - 提供 Electron IPC 和本地 Python 执行能力
- `apps/desktop/python/image-tools`
  - 负责桌面端的实际图片处理

### 不推荐的方案

以下方案不推荐采用：

- 在 `packages/modules/工具` 中大量写 `if (桌面端) else if (云端)` 并混入 Electron 细节
- 为桌面端复制一套 `图片编辑工作台.vue`、`图片转换工作台.vue`、`图片拼接工作台.vue`
- 只在“导出时”切换到本地后端，而导入和预览仍强依赖浏览器解码

第三种方案的问题最明显。因为很多增强格式首先卡在“源文件无法稳定读入”，不是卡在导出。

## 能力模型设计

### 核心思路

能力模型不要只描述“能导出什么格式”，还要描述以下几个维度：

- 可导入格式
- 可导出格式
- 是否支持动画读取
- 是否支持动画导出
- 是否保留元数据
- 是否支持透明通道
- 预览图是否需要后端生成

### 推荐类型定义

建议在 `packages/platform` 中定义统一类型。

```ts
export type 图片格式能力 = {
  mimeType: string
  扩展名: string[]
  可导入: boolean
  可导出: boolean
  支持透明: boolean
  支持动画: boolean
  保留元数据: boolean
}

export type 图片工具能力 = {
  运行时: 'browser' | 'desktop'
  支持后端增强: boolean
  导入格式: 图片格式能力[]
  导出格式: 图片格式能力[]
  支持预览代理: boolean
  支持拼接: boolean
  支持编辑: boolean
  支持批量转换: boolean
}
```

页面只消费能力，不直接写死完整格式列表。

## 统一服务接口设计

建议将图片编辑、转换、拼接统一为一个图片工具服务，而不是拆成三套完全独立的服务。

### 服务接口

```ts
export type 图片资源句柄 = {
  id: string
  原始文件名: string
  原始MimeType: string
  宽度: number
  高度: number
  是否动画: boolean
  预览地址: string
  元数据摘要?: {
    hasExif: boolean
    hasIcc: boolean
  }
}

export type 图片编辑参数 = {
  旋转角度: number
  水平翻转: boolean
  垂直翻转: boolean
  裁剪区域?: {
    x: number
    y: number
    width: number
    height: number
  }
  输出宽度?: number
  输出高度?: number
}

export type 图片拼接参数 = {
  布局: 'horizontal' | 'vertical' | 'grid'
  间距: number
  背景: {
    type: 'transparent' | 'solid'
    color?: string
  }
  对齐方式: 'start' | 'center' | 'end'
}

export type 图片导出参数 = {
  mimeType: string
  quality?: number
  保留元数据?: boolean
  保持动画?: boolean
}

export interface 图片工具服务 {
  获取能力(): Promise<图片工具能力>
  导入图片(input: File[]): Promise<图片资源句柄[]>
  从桌面路径导入图片?(paths: string[]): Promise<图片资源句柄[]>
  执行转换(resourceId: string, options: 图片导出参数): Promise<Blob | 桌面文件结果>
  执行编辑(resourceId: string, edit: 图片编辑参数, output: 图片导出参数): Promise<Blob | 桌面文件结果>
  执行拼接(resourceIds: string[], stitch: 图片拼接参数, output: 图片导出参数): Promise<Blob | 桌面文件结果>
  释放资源(resourceIds: string[]): Promise<void>
}
```

## 浏览器端实现建议

### 作用

浏览器端实现继续承担云端和普通 Web 环境的图片能力，特点是：

- 无需本地依赖
- 直接处理 `File` / `Blob`
- 预览与导出都在前端完成

### 范围

浏览器端建议继续支持：

- 导入：`PNG / JPG / WEBP / AVIF / GIF(首帧)`
- 导出：`PNG / JPG / WEBP / AVIF`

同时明确保留现有限制：

- 动图 `GIF` 默认只取首帧，除非后续专门引入 wasm 方案
- 默认不保留 `EXIF / ICC / 拍摄信息`
- 不承诺支持 `HEIC / TIFF / PSD`

### 实现位置

建议新增：

- `packages/platform/src/image-tools/browser.ts`

由它封装当前几个工作台中基于 `canvas` 的共通逻辑，避免页面直接操作图像导出。

## 桌面端实现建议

### 总体思路

桌面端不建议仅在导出时调用后端，而是将“增强格式导入、预览生成、最终导出”统一交给本地能力。

页面依旧保留现有交互，但桌面增强格式的底层数据流改成：

1. 用户选择图片
2. 前端把本地路径交给 Electron
3. 主进程调用 Python 工具读取源图
4. Python 工具生成预览图和源图元数据
5. 前端使用预览图继续编辑或拼接
6. 用户点击导出时，前端仅提交参数
7. Python 工具对原图执行最终处理并输出结果

### 为什么不能只在导出时切到后端

如果源文件本身浏览器读不进来，那么编辑和拼接阶段就无法开始。例如：

- `HEIC`
- `PSD`
- 部分 `TIFF`
- 动态 `GIF`

所以导入和预览必须纳入桌面后端能力范围。

## Electron 侧设计

### preload 暴露接口

建议新增以下 API：

```ts
imageToolsGetCapabilities: () => ipcRenderer.invoke('desktop:image-tools:get-capabilities')
imageToolsImportFromPaths: (paths) => ipcRenderer.invoke('desktop:image-tools:import-from-paths', paths)
imageToolsConvert: (request) => ipcRenderer.invoke('desktop:image-tools:convert', request)
imageToolsEdit: (request) => ipcRenderer.invoke('desktop:image-tools:edit', request)
imageToolsStitch: (request) => ipcRenderer.invoke('desktop:image-tools:stitch', request)
imageToolsRelease: (resourceIds) => ipcRenderer.invoke('desktop:image-tools:release', resourceIds)
imageToolsSelectInputs: () => ipcRenderer.invoke('desktop:image-tools:select-inputs')
imageToolsSelectOutputPath: (options) => ipcRenderer.invoke('desktop:image-tools:select-output-path', options)
```

### 主进程 IPC 命名

建议统一使用：

- `desktop:image-tools:get-capabilities`
- `desktop:image-tools:select-inputs`
- `desktop:image-tools:select-output-path`
- `desktop:image-tools:import-from-paths`
- `desktop:image-tools:convert`
- `desktop:image-tools:edit`
- `desktop:image-tools:stitch`
- `desktop:image-tools:release`

这样命名规则与现有 `desktop:image-classifier:*` 风格一致。

### 输出策略

桌面端建议优先输出到文件路径，而不是把大图完整回传给渲染进程。

推荐两种结果：

- 预览阶段：返回预览图路径或临时文件 URL
- 最终导出阶段：直接写入用户选定路径，并返回结果摘要

推荐返回结构：

```ts
type 桌面文件结果 = {
  outputPath: string
  outputMimeType: string
  outputSize: number
}
```

这样可以避免大文件通过 IPC 传输，降低内存压力。

### 打包与资源定位

桌面端图片工具、图片分类工具、Minecraft 工具都依赖本地 Python 子目录。

开发环境下可以直接从仓库路径读取：

- `apps/desktop/python/image-tools`
- `apps/desktop/python/ai-media-processor`
- `apps/desktop/python/minecraft-tool`

但进入 Electron 安装包后，不能继续假定仓库目录结构仍然存在，因此主进程必须同时支持两套定位策略：

1. 开发环境
   - 通过仓库根目录定位 `apps/desktop/python/*`
2. 打包环境
   - 通过 `process.resourcesPath/python/*` 定位随安装包带上的资源目录

当前实现建议：

- `electron-builder` 通过 `extraResources` 将三个 Python 子工具复制到：
  - `resources/python/ai-media-processor`
  - `resources/python/image-tools`
  - `resources/python/minecraft-tool`
- 主进程统一通过“开发目录优先，打包资源目录兜底”的方式解析入口脚本

这样可以保证：

- 开发阶段无需改现有目录结构
- 打包后不会再因为仓库根目录不存在而找不到 `main.py`

### 当前打包局限

目前这一步只解决了“脚本目录进安装包”和“运行时能找到脚本”的问题，还没有解决“Python 解释器和依赖随包分发”的问题。

也就是说，当前桌面增强能力在安装包环境下仍然默认依赖：

- 用户机器存在可用的 `python` / `python3` / `py -3`
- 对应环境已安装图片工具依赖

例如图片工具至少要有：

- `Pillow`
- `pillow-heif`
- `pillow-avif-plugin`
- `psd-tools`

这意味着当前状态更准确地说是：

- `已支持开发环境`
- `已支持安装包内脚本定位`
- `尚未完成真正的无依赖分发`

如果后续要做到“安装即用”，建议再补一层真正的分发方案，常见做法有两种：

1. 将 Python 子工具冻结成独立可执行文件
   - 可用 `PyInstaller`、`Nuitka`
   - Electron 只负责调用 `exe`
2. 随安装包附带一套受控 Python 运行时与依赖目录
   - 主进程固定调用内置解释器
   - 同时把依赖 wheel 或 site-packages 一起带上

对于当前自用项目，优先级建议是：

1. 先把图片工具能力做稳定
2. 再统一把三个 Python 子工具收敛到一套可执行分发方案
3. 最后再处理增量更新、签名和体积优化

### 当前 embedded 模式约定

当前桌面端支持 `system / embedded` 两种 Python 模式。

- `system` 使用系统里的 `python` / `python3` / `py -3`
- `embedded` 使用 `apps/desktop/python-runtime/python/python.exe`

打包后对应路径为：

- `resources/python-runtime/python/python.exe`

当前现状：

- 启动和构建都支持 `--python-mode embedded`
- `--prepare-python-runtime` 会通过官方安装器准备运行时
- 构建时会把 `apps/desktop/python-runtime` 复制到安装包资源目录
- 仓库默认不提交完整运行时二进制
- 最终分发给用户时，只复制运行时文件，不会在用户机器再次执行安装器

## Python 子工具设计

### 目录建议

建议新增：

- `apps/desktop/python/image-tools/`

参考现有图片分类工具的组织方式：

- `main.py`
- `pyproject.toml`
- `README.md`
- `src/`

### 功能划分

建议 Python 侧提供一个统一入口，而不是分散成很多无协议脚本。

推荐命令：

- `capabilities-json`
- `import-json`
- `convert-json`
- `edit-json`
- `stitch-json`
- `release-json`

### 命令协议示例

```bash
python main.py capabilities-json
python main.py import-json --payload-file xxx.json
python main.py convert-json --payload-file xxx.json
python main.py edit-json --payload-file xxx.json
python main.py stitch-json --payload-file xxx.json
```

主进程将请求写入临时 JSON 文件，再让 Python 读取该文件，执行后输出 JSON 结果。

这种方式与现有桌面图片分类工具的做法一致，也更稳。

## Python 技术选型建议

### 首选

推荐优先使用以下组合：

- `Pillow`
- `pillow-heif`
- `pillow-avif-plugin`
- `psd-tools`

在多数场景下已经够用。

### 可选补充

按需要再补：

- `tifffile`
- `imageio`
- `pyvips`

### 各格式建议

- `PNG / JPG / WEBP`
  - `Pillow` 即可
- `AVIF`
  - 优先 `pillow-avif-plugin`
- `HEIC / HEIF`
  - `pillow-heif`
- `TIFF`
  - `Pillow` 为主，复杂场景再补 `tifffile`
- `PSD`
  - `psd-tools` 读取，导出平铺结果
- `GIF`
  - 静态导出很容易
  - 动图导出和编辑要单独标记能力，不建议第一期全做
- `ICO`
  - 可作为导出格式支持
- `BMP`
  - 读写难度低，可直接纳入第一期

## 预览策略

### 普通浏览器可读格式

对于浏览器本来就能读的格式：

- 可以直接沿用现有前端预览
- 也可以统一走桌面后端生成预览，但第一期不必强求

### 浏览器不易读取格式

对于增强格式：

- 由 Python 生成预览图
- 预览图格式建议固定为 `PNG` 或 `WEBP`
- 前端只展示预览图，不直接依赖浏览器读取原始文件

### 编辑参数与原图分离

前端在编辑时只维护参数，不直接把预览图当作最终源数据：

- 裁剪框
- 旋转角度
- 翻转状态
- 缩放尺寸
- 拼接布局

最终导出时，桌面后端以原始文件为输入，应用这些参数后输出目标文件。

这是保证增强格式质量和一致性的关键。

## 三个工作台的改造建议

### 图片转换

第一优先级改造对象。

目标：

- 导入更多源格式
- 导出更多目标格式
- 保留批量转换能力
- 桌面端支持写入用户指定目录

建议：

- 浏览器端仍保留现在的下载式导出
- 桌面端改为“选择输出目录后批量生成文件”
- 批量转换时前端只展示任务进度和结果列表

### 图片编辑

第二优先级改造对象。

目标：

- 让特殊格式也能进入编辑流程
- 保持当前裁剪、旋转、翻转等交互模式

建议：

- 前端继续渲染预览画布
- 增强格式通过桌面后端生成预览图
- 导出结果统一由桌面后端根据原图和参数重新计算

### 图片拼接

第三优先级改造对象。

目标：

- 让更多源格式可参与拼接
- 最终导出支持更多格式

建议：

- 普通格式仍可直接前端预览布局
- 增强格式导入后获取尺寸和预览图
- 实际拼接结果由桌面后端依据源图重新渲染

## 页面与交互层建议

### 不复制页面

不建议新建一套桌面版 `图片工具页面.vue`。

推荐继续共用：

- `图片工具页面.vue`
- `图片转换工作台.vue`
- `图片编辑工作台.vue`
- `图片拼接工作台.vue`

### 页面只感知能力

页面只应该知道：

- 当前运行时支持哪些格式
- 当前操作是否由本地后端增强
- 当前导出是否保留元数据
- 当前格式是否支持动画

页面不应该知道：

- Electron IPC 细节
- Python 命令参数拼装细节
- 临时文件目录如何管理

## 与现有模块的关系

### `packages/modules/工具`

职责调整为：

- 保留页面和工作台组件
- 抽走内部直接图像导出逻辑
- 改为调用统一图片工具服务

### `packages/platform`

建议作为图片工具运行时适配层放置位置。

理由：

- 这是明确的平台差异能力
- 浏览器和桌面实现都属于平台适配
- 与项目中“平台能力抽象与适配层”的职责一致

### `apps/desktop`

仅放桌面专属能力：

- Electron IPC
- 本地 Python 执行
- 桌面文件选择与输出路径选择

这也符合“通用内容放到 packages，apps 里只放平台相关内容”的约定。

## 分阶段实施建议

### 第一阶段

- 抽离统一类型和能力接口
- 将图片转换工作台改为通过服务接口导出
- 保留浏览器端实现
- 桌面端先只做格式转换增强

目标：

- 最快打通端到端能力链路
- 先验证 Electron + Python 图片工具方案

### 第二阶段

- 图片编辑工作台接入统一服务
- 增强格式走“预览图 + 参数导出”
- 补齐桌面编辑导出能力

### 第三阶段

- 图片拼接工作台接入统一服务
- 支持更多源格式参与拼接
- 根据需要补充批量输出和进度反馈

### 第四阶段

- 进一步支持动画 GIF 保留
- 增加元数据保留开关
- 增加更复杂的格式策略

## 推荐的第一期格式范围

为了控制复杂度，第一期建议桌面增强只先覆盖这些格式：

- 导入新增：`HEIC / HEIF / TIFF / PSD / BMP / ICO`
- 导出新增：`BMP / ICO / TIFF`

保守处理：

- `GIF` 第一阶段只支持首帧静态处理，先不承诺动画保留
- `PSD` 第一阶段只读取合成结果，不处理图层编辑
- `EXIF / ICC` 第一阶段先以“尽量保留”为目标，但不要一开始承诺全部格式都完整保留

## 风险与注意事项

### 依赖安装复杂度

部分图片库在不同系统上安装难度不同，尤其是：

- `pillow-heif`
- `pyvips`
- `libvips` 相关依赖

建议第一期优先选安装链路更稳的库。

### 大图内存占用

如果把大图数据通过 IPC 直接传输到渲染进程，内存压力会很高。

因此应优先采用：

- 预览返回临时文件
- 最终导出直接写入目标路径

### 预览与最终结果差异

预览图如果经过压缩，可能与最终结果略有差异。

需要在文档和提示里明确：

- 预览用于交互
- 最终导出以原图高质量处理结果为准

### 临时文件清理

桌面端生成预览图和中间文件后，需要定义清理策略：

- 页面关闭时释放
- 重新导入时释放旧资源
- 主进程兜底清理过期临时文件

## 最终建议

推荐采用以下总策略：

- 共用现有图片工具页面
- 抽离统一图片工具服务
- 浏览器端保留当前前端实现
- 桌面端新增 Electron IPC + 本地 Python 图片处理器
- 导入、预览、编辑导出、拼接导出统一纳入桌面增强能力

不推荐复制一套桌面页面，也不推荐只在导出时补后端。

如果按实施收益排序，建议优先级为：

1. 图片转换增强
2. 图片编辑增强
3. 图片拼接增强

这样可以先用最小成本验证整条技术路径，再逐步把其余两个工作台迁移过去。
