# 前端重构方案

## 结论

截至 2026-04-18，当前前端已经**需要重构**，但**不建议整站推倒重写**。

更合适的方向是：

1. 保留现有基础设施与技术栈
2. 允许破坏性调整路由、页面拆分和目录结构
3. 按业务域分阶段重构，而不是一次性重写全部页面

原因很简单：当前项目的底层并没有坏，真正的问题集中在页面层过胖、分层不统一、业务边界不够清晰。

- `frontend/package.json`
- `frontend/src/main.ts`

这说明当前前端的主要问题不是“代码已失控到无法工作”，而是“结构已经开始拖慢后续开发”。

## 当前判断依据

## 1. 基础设施层基本健康

应用入口、初始化流程、鉴权恢复、主题和设置初始化都比较清晰。

- [frontend/src/main.ts](../frontend/src/main.ts)
- [frontend/src/app/bootstrap.ts](../frontend/src/app/bootstrap.ts)
- [frontend/src/router/index.ts](../frontend/src/router/index.ts)
- [frontend/src/utils/api.ts](../frontend/src/utils/api.ts)

这部分没有明显必要重写。继续保留即可。

## 2. 页面层明显过胖

当前前端源码文件中：

- 超过 1000 行的 `.vue/.ts` 文件有 10 个
- 超过 500 行的 `.vue/.ts` 文件有 28 个

其中最典型的页面包括：

- [frontend/src/views/dashboard/FilesPage.vue](../frontend/src/views/dashboard/FilesPage.vue)
- [frontend/src/views/dashboard/TodosPage.vue](../frontend/src/views/dashboard/TodosPage.vue)
- [frontend/src/views/dashboard/CollectionsPage.vue](../frontend/src/views/dashboard/CollectionsPage.vue)
- [frontend/src/views/dashboard/BillsPage.vue](../frontend/src/views/dashboard/BillsPage.vue)
- [frontend/src/views/dashboard/ArticleEditor.vue](../frontend/src/views/dashboard/ArticleEditor.vue)
- [frontend/src/views/dashboard/SystemPage.vue](../frontend/src/views/dashboard/SystemPage.vue)

这些页面往往同时承担：

- 页面状态管理
- 表单状态
- API 调用
- 弹窗编排
- 列表筛选
- 批量操作
- 提示消息
- 局部业务规则

页面承担职责过多，会带来几个直接问题：

1. 修改一个需求时，很难快速确认影响范围
2. 复用困难，很多逻辑只能复制粘贴
3. 单文件过大，阅读和调试成本高
4. 后续想补测试时切入点很差

## 3. 分层方式不统一

文件管理模块已经开始向按业务拆分靠拢，例如：

- [frontend/src/views/dashboard/FilesPage.vue](../frontend/src/views/dashboard/FilesPage.vue)
- [frontend/src/features/files/explorer/files-explorer.actions.ts](../frontend/src/features/files/explorer/files-explorer.actions.ts)
- [frontend/src/features/files/explorer/files-explorer.data-actions.ts](../frontend/src/features/files/explorer/files-explorer.data-actions.ts)
- [frontend/src/features/files/explorer/files-explorer.selection.ts](../frontend/src/features/files/explorer/files-explorer.selection.ts)

这说明项目已经在往正确方向演进。

但其他业务域没有统一跟上，例如：

- `todos` 仍然大量保留页面内编排逻辑
- `bills`、`collections` 仍然以大页面为主
- 成功/失败提示、确认弹窗、数据加载流程分散在多个页面内

也就是说，目前前端不是“完全没有结构”，而是“有些模块开始规范化，有些模块还停留在大页面堆逻辑阶段”。

## 4. Blog 路由语义不够清晰

当前博客区路由是：

- `/blog`
- `/blog/:slug`

但这两个路由都指向同一个页面：

- [frontend/src/router/index.ts](../frontend/src/router/index.ts)
- [frontend/src/views/blog/BlogHome.vue](../frontend/src/views/blog/BlogHome.vue)

同时，`BlogHome.vue` 内又通过 `viewMode` 管理多种模式：

- feed
- archive
- announcements
- friends
- about
- sponsor
- bangumi
- gallery
- rss

这会导致两个问题：

1. 路由层表达的业务语义不清楚
2. 页面层承担了过多的“子路由容器”职责

这类结构短期开发快，但长期维护会越来越难拆。

## 是否允许完全重构

允许。

因为这个项目是自用项目，且已有明确约定：**可以重构，不必向前兼容**。

但“允许完全重构”不代表“现在最优方案就是整站重写”。

当前更优策略是：

- 保留技术栈
- 保留基础设施
- 允许破坏性调整目录结构、页面拆分、路由设计和状态组织方式
- 按业务域分阶段替换旧实现

这样可以避免一次性重写带来的长时间停摆，也能持续验证重构方向。

## 不建议整站重写的原因

如果现在整站重写，收益未必比成本大，主要原因有：

1. 当前技术栈并不过时，`Vue 3 + Vite + Pinia + TypeScript + Element Plus` 仍可继续使用
2. 鉴权、主题、设置、API 封装、启动流程没有明显架构问题
3. 一次性重写会把“结构改造”和“业务回归”混在一起，风险过大
4. 目前最严重的问题集中在少数大页面，不是全项目每一层都烂掉

所以更合适的是“破坏性重构”，不是“重做一个新前端”。

## 推荐重构目标

重构后的前端应满足以下目标：

1. 页面只负责装配，不直接堆业务流程
2. 路由按业务语义表达，不让单页面承载过多模式切换
3. API、类型、状态、视图编排、纯逻辑函数分层明确
4. 相同模式的业务页采用统一组织方式
5. 新功能默认落到业务域目录，不再继续堆到超大页面中

## 推荐目录方向

建议逐步统一到下面这种组织方式：

```text
frontend/src
  app/
  router/
  components/
  composables/
  styles/
  utils/
  features/
    auth/
    blog/
      api/
      components/
      composables/
      routes/
      store/
      types/
    todos/
      api/
      components/
      composables/
      store/
      types/
      utils/
    files/
      api/
      explorer/
      components/
      composables/
      store/
      types/
    bills/
    collections/
    articles/
    comments/
    friend-links/
```

核心原则：

- 通用组件留在 `components`
- 业务组件进入 `features/<domain>/components`
- 页面级编排进入 `features/<domain>/routes` 或 `views`
- 纯逻辑放到 `composables` 或 `utils`
- 状态不要散落在超大页面里

## 推荐实施顺序

## 第一阶段：先拆路由和页面边界

优先处理博客区和控制台大页面。

建议先拆：

1. `BlogHome.vue`
2. `TodosPage.vue`
3. `CollectionsPage.vue`
4. `BillsPage.vue`

目标：

- 让每个页面先缩下来
- 先把“一个页面承担多个模式”的问题拆掉
- 先建立统一的业务域目录结构

## 第二阶段：统一业务域结构

将 `todos`、`bills`、`collections`、`articles` 统一改造成类似 `files` 的结构化组织。

每个业务域至少明确拆出：

- `api.ts`
- `types.ts`
- 业务状态
- 页面编排 composable
- 业务组件
- 与 UI 无关的纯逻辑

## 第三阶段：收敛公共模式

当业务域拆分完成后，再处理重复模式：

- 列表页加载态
- 错误提示
- 成功提示
- 删除确认
- 批量操作编排
- 查询参数与页面状态同步

这一步不应该太早做，否则容易在旧结构上抽错公共层。

## Blog 区域建议

Blog 区域建议优先从“单页多模式”改为“显式路由”。

建议方向：

- `/blog`
- `/blog/archive`
- `/blog/announcements`
- `/blog/friends`
- `/blog/about`
- `/blog/sponsor`
- `/blog/bangumi`
- `/blog/gallery`
- `/blog/rss`
- `/blog/:slug`

好处：

1. 路由即业务语义
2. 页面职责更单一
3. 各页面可以独立加载和拆分
4. 后续做权限、埋点、缓存时更自然

## Dashboard 区域建议

控制台页面建议采用“容器页 + 业务组件 + 编排 composable”的模式。

以 `todos` 为例，目标不是继续往 `TodosPage.vue` 里加逻辑，而是拆成：

- 页面容器
- 筛选状态
- 表单状态
- 回收站状态
- 导入导出流程
- 批量操作流程
- 各视图组件

这样每一块都能单独维护，不需要每次进一个 2000 行文件里找逻辑。

## 哪些部分可以暂时不动

以下部分当前没有明显必要推倒：

- `main.ts`
- `app/bootstrap.ts`
- `utils/api.ts`
- `stores/auth.ts`
- 主题与外观初始化相关 store
- 已经拆出较多逻辑的 `files/explorer`

这些内容可以作为重构时期的稳定底座使用。

## 重构完成后的验收标准

建议把下面这些作为阶段性验收标准：

1. 核心业务页面不再出现 1500 行以上单文件
2. 页面文件不再直接堆积大量 API 编排和业务流程
3. Blog 路由不再依赖单页面 `viewMode` 承载多模块
4. 新增业务功能默认进入对应 `features/<domain>` 目录
5. `npm run lint` 与 `npm run typecheck` 持续通过

## 一句话结论

当前前端值得重构，而且可以做破坏性重构。

但从实际情况看，**最优方案不是整站推倒重写，而是按业务域分阶段重构，优先拆 BlogHome、TodosPage、CollectionsPage、BillsPage 和 ArticleEditor 这类超大页面。**
